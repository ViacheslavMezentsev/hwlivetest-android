## 1. Цель и принципы

HW Live Test — «помощник в кармане» для работы с платой, на которой идёт прошивка. Телефон
подключается к плате через отладчик, логический анализатор, USB-UART или собственный прибор,
показывает и записывает происходящее, а агент помогает разобраться.

Принципы, которые действуют во всех модулях:

- **Только наблюдение.** Приложение не пишет в память MCU, не останавливает и не сбрасывает ядро.
  Всё, что меняет состояние цели (запись, halt, reset, передача в UART, переключение DTR/RTS), —
  отдельная функция, которая включается явно и согласуется отдельно.
- **Без внешних программ.** Никаких Termux, OpenOCD, GDB, sigrok в рантайме. Протоколы приборов
  реализуются на Kotlin поверх Android `UsbManager`.
- **Протокол — чистый Kotlin/JVM.** Всё, что не касается Android, живёт в модулях без зависимостей
  от Android и проверяется на JVM, в том числе по записям реального обмена (`captures/`).
- **Данные — это доказательства.** Всё, что показано, можно записать в MCAP с общей шкалой времени и
  открыть в Foxglove или PlotJuggler.
- **Приватность.** Серийные номера приборов и UID микроконтроллеров не читаются и не сохраняются.
- **Работает офлайн.** Сеть нужна только агенту и отправке файлов.

## 2. Слои платформы

```text
┌───────────────────────────────────────────────────────────────┐
│ Интерфейс     Compose Multiplatform: чаты-сессии, графики,     │
│               лента логического анализатора, терминал          │
├───────────────────────────────────────────────────────────────┤
│ Агент         инструменты агента = операции приборов и анализа │
├───────────────────────────────────────────────────────────────┤
│ Сессии        тестовая сессия (чат), папки, карточки-рецепты   │
├───────────────────────────────────────────────────────────────┤
│ Доказательства запись MCAP: каналы, вложения, метаданные       │
├───────────────────────────────────────────────────────────────┤
│ Анализ        эвристики «ПУСК», декодеры протоколов, оси,      │
│               пирамида детализации, статистика                 │
├───────────────────────────────────────────────────────────────┤
│ Потоки        типизированные потоки с общей шкалой времени     │
├───────────────────────────────────────────────────────────────┤
│ Приборы       ST-Link · логический анализатор · USB-UART ·     │
│               датчики телефона · собственные приборы           │
├───────────────────────────────────────────────────────────────┤
│ USB           реестр устройств, разрешения, общий доступ к     │
│               составному устройству, bulk/control/async        │
└───────────────────────────────────────────────────────────────┘
```

Зависимости направлены только вниз. Нижние слои ничего не знают о сессиях, агенте и экранах: прибор
отдаёт потоки, а что с ними делать — решают верхние слои.

### 2.1. USB

Реестр подключённых устройств (`UsbManager.deviceList` и события подключения и отключения), запрос
разрешений, открытие `UsbDeviceConnection`. Интерфейсы составного устройства раздаются разным
драйверам: у ST-Link V2-1 на Nucleo в одном устройстве есть отладка, VCP (CDC-ACM) и накопитель, и
отладка с терминалом должны работать одновременно. Каждый драйвер открывает своё соединение и
захватывает только свои интерфейсы; если Android этого не позволит, соединение станет общим
(ТЗ ST-Link, допущение 10.1.4).

### 2.2. Приборы

Драйвер прибора знает протокол своего устройства и ничего больше. Каждый прибор работает в своём
потоке исполнения (один поток на прибор), поэтому медленный или зависший прибор не мешает остальным.

### 2.3. Потоки

Прибор публикует один или несколько потоков. Виды потоков:

| Поток | Пример источника | Содержимое |
| :--- | :--- | :--- |
| Скаляр | поле из `addresses.json`, датчик телефона | время + число |
| Логические отсчёты | логический анализатор | частота, маска каналов, блок отсчётов |
| Байты | USB-UART, VCP | время прихода блока + байты |
| События | эвристики, декодеры, отключение прибора | время + структура |
| Медиа | камера, микрофон (с разрешения) | кадры H.264/H.265, звук |

У каждого потока — имя в пространстве имён прибора (`/stlink0/rpm`, `/la0/d3`, `/uart0/rx`), тип и
метка времени в общей шкале (п. 4.3).

### 2.4. Анализ

Чистые функции над потоками: эвристики «ПУСК» (`diag`), декодеры протоколов в духе Saleae Protocol
Analyzer SDK (UART, I²C, SPI, CAN — поверх логических отсчётов или байтов), пирамида детализации для
быстрой прокрутки миллионов отсчётов, статистика, разбор текстовых строк UART в числовые поля.

### 2.5. Доказательства

`recorder` пишет MCAP: каналы потоков, схемы ROS 1 для скаляров, свои схемы для логических отсчётов
и байтов, Foxglove `CompressedVideo` и аудио для медиа, вложения (журнал обмена, `addresses.json`,
отчёт «ПУСК»), метаданные сессии (модель прибора, опознанный MCU, версия приложения).

### 2.6. Сессии

Тестовая сессия — это чат: в ленте идут карточки (отчёт «ПУСК», снимок графика, захват анализатора,
фрагмент терминала, заметка, ответ агента). Сессии группируются в папки. Карточку-рецепт («снять 2 с
UART на 115200 и найти ошибки кадра») можно переслать в другую сессию и повторить. Каждая сессия
ссылается на свои файлы MCAP.

### 2.7. Агент

Агент получает инструменты — те же операции, что доступны пользователю: опознать цель, прочитать
поле, снять захват, декодировать, найти аномалии. Ограничение «только наблюдение» действует и для
агента: инструменты, меняющие цель, ему не выдаются без отдельного согласия пользователя.

### 2.8. Интерфейс

Compose Multiplatform (отрисовка Skia). Сейчас экраны написаны на Android View; переход на Compose —
этап 6 (раздел 10). Графики и лента анализатора рисуются на `Canvas` по данным пирамиды детализации.
AGG служит образцом алгоритмов (сглаживание, растеризация), но не движком.

## 4. Ключевые абстракции

Эскизы на Kotlin — информативные; окончательные сигнатуры фиксируются в ТЗ модулей и в коде.

### 4.1. Прибор

```kotlin
/** Устойчивое имя прибора в пределах сессии: stlink0, la0, uart1. */
@JvmInline value class InstrumentId(val value: String)

interface Instrument : AutoCloseable {
    val id: InstrumentId
    val kind: InstrumentKind            // DEBUG_PROBE, LOGIC_ANALYZER, SERIAL, SENSOR, CUSTOM
    val title: String                   // «ST-Link/V2-1 → STM32F411»
    val state: StateFlow<InstrumentState>
    val streams: List<StreamInfo>       // что прибор умеет публиковать
    fun open()                          // в своём потоке исполнения
    override fun close()                // идемпотентно, в том числе после отключения кабеля
}
```

### 4.2. Поток

```kotlin
data class StreamInfo(
    val topic: String,          // "/stlink0/rpm"
    val type: StreamType,       // SCALAR, LOGIC, BYTES, EVENT, MEDIA
    val unit: String? = null,
)

interface StreamSink<T> {
    fun onData(timeNs: Long, value: T)  // время — в общей шкале (п. 4.3)
}
```

### 4.3. Время

Общая шкала — `SystemClock.elapsedRealtimeNanos()` телефона: она монотонна и не прыгает при смене
часов. У каждого прибора свои часы:

- ST-Link: время отсчёта — середина интервала между отправкой команды и приходом ответа; погрешность
  — половина длительности обмена (порядка 1 мс на полноскоростном USB);
- логический анализатор: точная внутренняя частота, привязка к телефону — по времени завершения
  передач USB и числу полученных отсчётов;
- UART: время прихода блока USB (погрешность — период опроса и задержка буфера моста).

Для точного совмещения приборов (например, фронт на анализаторе и значение счётчика в памяти)
прошивка может дёргать маркер-GPIO: анализатор видит фронт, ST-Link читает счётчик маркеров. Метод
описан в ТЗ анализатора.

### 4.4. Карточка сессии

```kotlin
sealed interface Card {
    val timeNs: Long
    val author: Author                  // USER, APP, AGENT
}
data class ReportCard(...) : Card       // «ПУСК»
data class ChartCard(...) : Card        // снимок графика + ссылка на каналы MCAP
data class CaptureCard(...) : Card      // захват анализатора + декодированные кадры
data class TerminalCard(...) : Card     // фрагмент UART
data class RecipeCard(...) : Card       // повторяемое действие с параметрами
```

## 5. Классы USB-приборов

Что Android-телефон может обслуживать сам через `UsbManager`, без root и драйверов ядра:

| Класс или прибор | Как опознаётся | Доступ из приложения | Ценность | План |
| :--- | :--- | :--- | :---: | :--- |
| ST-Link V2/V2-1/V3 | VID:PID ST | vendor bulk | высокая | есть |
| CMSIS-DAP v2 (DAPLink, Picoprobe, WCH-Link) | интерфейс «CMSIS-DAP», bulk | vendor bulk | высокая | после этапа 5 |
| Логический анализатор FX2 (fx2lafw) | VID:PID | control + bulk | высокая | ТЗ |
| USB-UART: CDC-ACM | класс 02/0A | bulk + control | высокая | ТЗ |
| USB-UART: CH340/CH341, CP210x, FT232/FT2232, PL2303 | VID:PID | vendor control + bulk | высокая | ТЗ |
| Свой прибор на BlackPill: vendor bulk | VID:PID, строка интерфейса | bulk | высокая | этап 7 |
| USB Audio (UAC) | класс 01 | системный звук: `AudioRecord` с выбранным USB-входом | средняя | этап 7 |
| HID (свой или мосты CP2112, MCP2221) | класс 03 | interrupt-точки после `claimInterface(force)` | средняя | по запросу |
| CAN: candleLight (gs_usb) | VID:PID | vendor bulk | средняя | по запросу |
| CAN: SLCAN | поверх CDC-ACM | через модуль UART | средняя | после UART |
| I²C/SPI-мосты CH341A, FT232H (MPSSE) | VID:PID | vendor control + bulk | низкая | по запросу |
| Накопитель (MSC) | класс 08 | только через SAF, если система смонтировала | низкая | нет |
| DFU STM32 | класс FE/01 | control | низкая | нет: запись в цель |
| Осциллографы на FX2 (Hantek 6022) | VID:PID | control + bulk | средняя | после анализатора |

Самодельные приборы на BlackPill (STM32F411, USB FS 12 Мбит/с) удобнее всего делать **составными**:
CDC-ACM для текстового журнала, vendor bulk для быстрых данных (АЦП, захват GPIO), при желании UAC
для звука. CDC и UAC телефон поддерживает почти без кода (терминал и системный звук), vendor bulk
даёт полную скорость и простой протокол. Для своих приборов предлагается один протокол самоописания:
первый запрос возвращает список потоков (имя, тип, единицы, частоту), после чего прибор сразу
появляется в платформе без нового драйвера.

## 6. Несколько приборов одновременно

### 6.1. Что нужно от программы

- **Реестр устройств.** Каждое устройство USB — отдельная запись с `deviceName` (путь на шине),
  VID:PID и моделью. Два ST-Link различаются по `deviceName`. Серийный номер не читается (раздел 1),
  поэтому после переподключения кабеля устройство опознаётся заново, а пользователь может дать ему
  метку («стенд 1»).
- **Свой поток исполнения на прибор.** Сейчас `Session` в `app` — одиночка с одним `worker`, одним
  ST-Link и одним списком полей; это главное, что придётся переделать (этап 1).
- **Свой ответ на каждый запрос разрешения.** Запрос разрешения USB сопоставляется с устройством по
  `EXTRA_DEVICE`, иначе при двух запросах подряд ответы перепутаются.
- **Пространство имён потоков.** `/stlink0/...`, `/stlink1/...`: в MCAP два прибора пишутся в один
  файл без конфликтов.
- **Фоновая служба.** Долгая запись идёт в foreground service типа `connectedDevice` (Android 14+
  требует объявленного типа), иначе система остановит приложение при выключенном экране.

### 6.2. Питание

Порт OTG телефона обычно рассчитан на ток до 500 мА, а на практике многие телефоны дают меньше и
отключают порт при перегрузке. Пассивный хаб делит этот же ток на всех.

Оценка потребления (порядок величин, уточнять USB-тестером):

| Устройство | Ток, мА |
| :--- | :---: |
| ST-Link V2 (клон) | 20–50 |
| ST-Link V2-1 на Nucleo вместе с платой | 100–200 |
| BluePill или BlackPill, питаемые от ST-Link | 20–60 каждая |
| Логический анализатор FX2 | 50–100 |

Вывод: два клона ST-Link с BluePill и BlackPill от пассивного хаба, скорее всего, заработают (около
200 мА), но запас мал, и любая нагрузка на плате (светодиоды, датчики, моторы) его съест. Надёжный
вариант — **хаб с внешним питанием**, который умеет одновременно заряжать телефон (OTG с проходной
зарядкой), либо отдельное питание плат при общей земле.

### 6.3. Пропускная способность

- ST-Link V2 и V2-1 — полноскоростные (12 Мбит/с); V3 — высокоскоростной (480 Мбит/с).
- Если хаб высокоскоростной, полноскоростные устройства за ним обслуживаются транслятором (TT). В
  хабе с **одним** TT все полноскоростные устройства делят 12 Мбит/с; в хабе с **несколькими** TT у
  каждого порта своя полоса. Для нескольких ST-Link V2 нужен хаб multi-TT.
- Логический анализатор на 24 МГц даёт 24 МБ/с — это большая часть реальной полосы USB 2.0 HS. Его
  лучше подключать отдельно или первым в хабе, остальным приборам оставить немного; навык WeAct
  прямо советует подключать анализатор без хаба. На частотах до 8 МГц хаб, как правило, не мешает.
- Телефон должен поддерживать USB 2.0 HS в режиме хоста. Это проверяется при подключении косвенно: у
  устройства, работающего на высокой скорости, bulk-точки имеют `maxPacketSize` 512 байт, на полной
  — 64.

### 6.4. Ответ на вопрос «2 отладчика: BluePill и BlackPill»

Да. Протокольная часть (`stlink`) уже не хранит глобального состояния: каждый `StLink` работает со
своим транспортом. Нужно: реестр устройств, сессия на прибор вместо одиночки `Session`, имена
потоков с префиксом прибора, экран со списком приборов. По питанию — см. п. 6.2, по полосе — два
ST-Link на 10 Гц опроса загружают шину на доли процента.

## 7. Масштабируемость: оценка и узкие места

Архитектура масштабируется по трём осям:

| Ось | Чем обеспечено | Что мешает сейчас |
| :--- | :--- | :--- |
| Новые виды приборов | интерфейс `Instrument`, протокол в чистом Kotlin, транспорт снаружи | нет общего модуля `instrument`; `usb` знает только ST-Link |
| Несколько приборов | поток исполнения и сессия на прибор, пространство имён потоков | одиночка `Session`, один `worker`, `Prefs` без прибора |
| Объём данных | потоки с метками времени, пирамида детализации, запись MCAP потоком | `TimeSeries` в памяти, MCAP пишется одним файлом на сессию |

Узкие места, которые программой не снять: ток OTG, полоса USB 2.0 и TT хаба, нагрев и батарея
телефона при долгой записи, ограничения Android на фоновую работу. Их платформа должна показывать
пользователю (ток неизвестен, но обрывы анализатора видны, скорость USB видна), а не прятать.

## 8. Принятые решения

| № | Решение | Почему |
| :---: | :--- | :--- |
| AD-01 | Протоколы приборов — на Kotlin поверх `UsbManager`, без OpenOCD, GDB, sigrok | без root и Termux; полный контроль обмена; проверяемость на JVM |
| AD-02 | Протокольные модули — чистый Kotlin/JVM | тесты по записям реального обмена, перенос на настольную платформу |
| AD-03 | Интерфейс — Compose Multiplatform (Skia); AGG — образец алгоритмов | отзывчивость, кроссплатформенность, готовый движок отрисовки |
| AD-04 | Доказательства — MCAP | стандарт индустрии; открывается Foxglove и PlotJuggler; медиа и вложения в одном файле |
| AD-05 | Только наблюдение по умолчанию | безопасность стенда; доверие к инструменту |
| AD-06 | Серийные номера и UID не читаются | приватность записей и журналов |
| AD-07 | Драйвер fx2lafw пишется заново, прошивка fx2lafw распространяется отдельным файлом | libsigrok — GPL-3.0+, наш проект — MIT (раздел 11) |
| AD-08 | Декодеры — свой API по мотивам Saleae SDK, без кода Saleae | лицензия SDK собственная; берём только идеи |
| AD-09 | Один прибор — один поток исполнения | изоляция зависаний и таймаутов |
| AD-10 | Интерфейсы составного устройства раздаются драйверам; у каждого своё соединение USB, общее — запасной вариант | составные устройства (ST-Link V2-1 + VCP, свои приборы); библиотека UART сама закрывает своё соединение |
| AD-11 | Датчики телефона — прибор `sensors`, видимый по умолчанию; камера и микрофон — только с разрешения | не требует разрешений; даёт контекст (вибрация, наклон, освещённость) |
| AD-12 | Свои приборы — на своей прошивке и известных протоколах (SUMP), без сторонних USB-стеков и библиотек | WeAct на FX2 не определился телефоном, причину внутри чужой платы не найти; своё звено диагностируемо |

## 9. ТЗ модулей

ТЗ составлены по одному шаблону: ревизии, нумерованные требования, тест-кейсы, матрица
прослеживаемости. Каждое ТЗ охватывает протокол и драйвер прибора; общие части (реестр USB, сессии,
запись MCAP) в них описаны только как интерфейсы.

| Модуль | ТЗ | Метод формирования |
| :--- | :--- | :--- |
| `stlink` + часть `usb` | [TECHNICAL_SPECIFICATION_STLINK.md](spec/TECHNICAL_SPECIFICATION_STLINK.md) | обратная разработка по коду, проверенному на оборудовании |
| `fx2la` | [TECHNICAL_SPECIFICATION_LOGIC_ANALYZER.md](spec/TECHNICAL_SPECIFICATION_LOGIC_ANALYZER.md) | с нуля |
| прибор на BlackPill и клиент SUMP | [TECHNICAL_SPECIFICATION_LA_PROBE.md](spec/TECHNICAL_SPECIFICATION_LA_PROBE.md) | с нуля, с планом экспериментов |
| `serial` | [TECHNICAL_SPECIFICATION_USB_UART.md](spec/TECHNICAL_SPECIFICATION_USB_UART.md) | с нуля |

Следующими кандидатами на ТЗ стоят `instrument` (реестр, сессия на прибор, потоки и время),
`decoders` и `session`.
