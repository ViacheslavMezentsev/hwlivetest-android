## 1. Введение

### 1.1. Назначение документа

1.1.1. Документ определяет требования к модулю поддержки логического анализатора на Cypress FX2
(CY7C68013A и совместимые, например CBM9002A) с открытой прошивкой fx2lafw: загрузка прошивки,
захват 8 цифровых каналов с частотой до 24 МГц, программный триггер, просмотр, измерения и запись.

1.1.2. Документ является основой для реализации и верификации кода: каждое требование имеет
уникальный номер, на который ссылаются комментарии в коде, тесты и матрица прослеживаемости (раздел
10).

### 1.2. Область применения

1.2.1. Требования применимы к модулю `fx2la` (протокол, захват, буфер, пирамида, экспорт) и к части
модуля `usb`, обслуживающей анализатор (асинхронный транспорт).

1.2.2. Документ не описывает декодеры протоколов (UART, I²C, SPI) — им посвящено отдельное ТЗ модуля
`decoders`; здесь описан только контракт доступа декодеров к отсчётам (п. 7.2). Отрисовка ленты на
экране описана как требования к данным для отрисовки, а не к виду экрана.

### 1.3. Метод формирования

1.3.1. Требования сформированы с нуля. Источники: описание WeAct LogicAnalyzerV1 и практика работы с
ним через sigrok-cli (навык `weact-logic-analyzer`), общедоступное описание протокола fx2lafw,
Technical Reference Manual Cypress EZ-USB FX2. Исходный код libsigrok (GPL-3.0+) не копируется и не
переводится; протокол реализуется по описанию и проверяется наблюдением обмена.

1.3.2. Маркеры происхождения применяются; поскольку кода модуля нет, все требования имеют маркер
`[N]`, кроме п. 3.1.1: он расширяет таблицу идентификаторов из задела `Fx2Ids` и помечен `[U]`.

1.3.3. В случае расхождения между этим документом и кодом расхождение считается дефектом одного из
них и разрешается пересмотром ревизии документа.

## 2. Общее описание

### 2.1. Контекст

2.1.1. Анализатор подключается к телефону по USB (напрямую или через хаб), его входы D0–D7 и GND — к
выводам платы. Анализатор только наблюдает: входы высокоомные, на цель он не влияет. При каждом
подключении в ОЗУ FX2 загружается прошивка fx2lafw, затем приложение задаёт частоту и получает
непрерывный поток отсчётов.

2.1.2. Параметры WeAct LogicAnalyzerV1: 8 каналов, до 24 МГц на всех каналах, входы 0–5,5 В (VIH > 2
В, VIL < 0,8 В), 1 байт на отсчёт. 8 МГц × 0,5 с = 4 МБ.

### 2.2. Функции модуля

2.2.1. Опознание анализатора и загрузка прошивки с обработкой ренумерации.

2.2.2. Захват с заданной частотой: фиксированной длины или непрерывный в кольцевой буфер.

2.2.3. Программный триггер по уровням и фронтам с предзаписью.

2.2.4. Пирамида детализации и быстрые запросы к захвату: фронты, уровни, интервалы.

2.2.5. Измерения: частота, скважность, длительность импульсов, статистика и джиттер.

2.2.6. Экспорт: MCAP, VCD, `.sr` (открывается PulseView).

### 2.3. Роли и потребители

| Роль | Взаимодействие |
| :--- | :--- |
| Экраны (`app`) | Настройка, запуск и остановка захвата, лента, курсоры, измерения. |
| Декодеры (`decoders`) | Чтение отсчётов по каналам и поиск фронтов (п. 7.2). |
| Запись (`recorder`) | Запись захвата и событий в MCAP. |
| Сессии и агент | Карточка захвата, повтор захвата по рецепту, вызов измерений. |

### 2.4. Границы

2.4.1. Вне области ТЗ: аналоговые каналы, 16-канальный режим, внешний тактовый вход, аппаратный
триггер, генерация сигналов, декодеры протоколов, вид экранов.

### 2.5. Ограничения платформы

2.5.1. Протокольная часть и обработка захвата (`fx2la`) — Kotlin/JVM без зависимостей от Android.

2.5.2. Доступ к USB — только Android USB Host API.

2.5.3. Прошивка fx2lafw распространяется по лицензии GPL-2.0+ и не входит в APK до решения
вопроса 11.2.1.

## 3. Протокол прибора

### 3.1. Опознание

3.1.1. Анализатором ДОЛЖНО считаться устройство с VID:PID из таблицы: `04B4:8613` (FX2 без
прошивки), `1D50:608C` (fx2lafw), `0925:3881` (WeAct LogicAnalyzerV1 и другие клоны Saleae Logic).
`[U]`

3.1.2. Таблица VID:PID ДОЛЖНА быть расширяемой без изменения логики (данными). `[N]`

3.1.3. Признаком загруженной прошивки ДОЛЖЕН считаться успешный ответ на запрос версии (п. 3.3.1), а
не VID:PID. Причина: у WeAct VID:PID не меняется после загрузки. `[N]`

### 3.2. Загрузка прошивки

3.2.1. Загрузка ДОЛЖНА выполняться управляющими запросами vendor OUT `0xA0` (тип `0x40`) с адресом
ОЗУ в `wValue`, порциями не более `FW_CHUNK_BYTES = 4096` байт, в порядке: (а) записать `0x01` в
регистр CPUCS `0xE600` (ядро FX2 в сбросе); (б) записать образ; (в) записать `0x00` в CPUCS
(запуск). `[N]`

3.2.2. Модуль ДОЛЖЕН принимать образ в двух форматах: двоичный файл `.fw` (загружается с адреса 0) и
Intel HEX (`.ihx`, `.hex`). `[N]`

3.2.3. Образ ДОЛЖЕН проверяться до загрузки: размер не более 16 КБ (ОЗУ кода FX2), адреса записей
HEX в пределах `0x0000…0x3FFF`. Образ, не прошедший проверку, НЕ ДОЛЖЕН загружаться. `[N]`

3.2.4. После запуска прошивки модуль ДОЛЖЕН ожидать ренумерацию не дольше `RENUM_TIMEOUT_MS = 3000`
мс: исчезновение устройства и появление нового с VID:PID из п. 3.1.1. Если устройство не исчезло, но
отвечает на запрос версии, ренумерация ДОЛЖНА считаться завершённой. `[N]`

3.2.5. Если после ренумерации система требует нового разрешения USB, модуль ДОЛЖЕН запросить его и
сообщить пользователю причину повторного запроса. `[N]`

3.2.6. Загрузка прошивки — запись в ОЗУ анализатора, а не в цель; она НЕ ДОЛЖНА требовать согласия
на действия, меняющие цель. `[N]`

3.2.7. SHA-256 загруженного образа и версия прошивки ДОЛЖНЫ сохраняться в метаданных захвата. `[N]`

### 3.3. Команды fx2lafw

3.3.1. Версия прошивки ДОЛЖНА читаться запросом vendor IN `0xB0` (`GET_FW_VERSION`), ответ 2 байта:
старшая и младшая части. Поддерживаемая старшая версия — `FX2LAFW_MAJOR = 1`; иная ДОЛЖНА давать
ошибку с указанием версии. `[N]`

3.3.2. Ревизия кристалла МОЖЕТ читаться запросом vendor IN `0xB2` (`GET_REVID_VERSION`), ответ 1
байт, для журнала. `[N]`

3.3.3. Захват ДОЛЖЕН запускаться запросом vendor OUT `0xB1` (`START`) с данными 3 байта: флаги,
старший и младший байты делителя. Флаги: бит 6 — опорная частота 48 МГц (0 — 30 МГц), бит 5 —
16-битные отсчёты (всегда 0 в этом модуле). `[N]`

3.3.4. Делитель ДОЛЖЕН вычисляться так: если 48 МГц делится на частоту нацело и
`48 МГц / f − 1 ≤ MAX_DELAY = 1536`, то опора 48 МГц и делитель `48 МГц / f − 1`; иначе, если
то же верно для 30 МГц, — опора 30 МГц; иначе частота ДОЛЖНА отвергаться. Контрольные значения —
в приложении C. `[N]`

3.3.5. Отсчёты ДОЛЖНЫ читаться из bulk IN точки `0x82` (EP2). `[N]`

3.3.6. Остановка захвата ДОЛЖНА выполняться прекращением чтения и отменой поставленных в очередь
запросов; повторный START ДОЛЖЕН начинать новый захват. `[N]`

### 3.4. Скорость шины

3.4.1. Скорость шины ДОЛЖНА определяться по `maxPacketSize` точки `0x82`: 512 байт — HS, 64 байт —
FS. `[N]`

3.4.2. На FS наибольшая частота ДОЛЖНА ограничиваться `FS_MAX_RATE = 500 кГц` с сообщением
пользователю «анализатор работает на полной скорости USB (12 Мбит/с): подключите его без хаба или
через хаб USB 2.0». `[N]`

3.4.3. Набор частот ДОЛЖЕН совпадать с приложением C; частота 48 МГц НЕ ДОЛЖНА предлагаться.
Причина: USB 2.0 её не выдерживает (обрывы потока). `[N]`

## 4. Захват и буфер

### 4.1. Поток данных

4.1.1. Чтение ДОЛЖНО выполняться асинхронно: в очереди постоянно стоят не менее `QUEUE_DEPTH = 16`
запросов `UsbRequest`, каждый размером `BUF_BYTES`; освободившийся запрос ставится в очередь
немедленно, до обработки его данных. `[N]`

4.1.2. `BUF_BYTES` ДОЛЖЕН быть 16384 байт на Android до 9 (API < 28) и 262144 байт на Android 9+.
Причина: до API 28 `UsbRequest.queue` ограничен 16 КБ. `[N]`

4.1.3. Объём очереди ДОЛЖЕН покрывать не менее 50 мс потока на выбранной частоте; при необходимости
глубина очереди увеличивается. `[N]`

4.1.4. Обработка данных (триггер, пирамида, запись) ДОЛЖНА выполняться в отдельном потоке от чтения
USB; поток чтения только переставляет буферы. `[N]`

### 4.2. Целостность

4.2.1. Модуль ДОЛЖЕН сравнивать число полученных отсчётов с ожидаемым по времени
(`частота × прошедшее время`). Отставание больше `GAP_TOLERANCE = 5 %` за окно 1 с ДОЛЖНО
сообщаться как «поток не успевает». `[N]`

4.2.2. Отсутствие данных дольше `STALL_MS = 500` мс во время захвата ДОЛЖНО останавливать захват с
ошибкой «обрыв потока»; полученные до обрыва отсчёты ДОЛЖНЫ сохраняться и помечаться как неполные.
`[N]`

4.2.3. Отключение анализатора во время захвата ДОЛЖНО завершать захват по п. 4.2.2 без зависания и
без потери уже полученных данных. `[N]`

### 4.3. Режимы

4.3.1. Захват фиксированной длины ДОЛЖЕН задаваться числом отсчётов или временем; останавливается
автоматически. `[N]`

4.3.2. Непрерывный захват ДОЛЖЕН писать в кольцевой буфер заданной длительности и продолжаться до
остановки пользователем или срабатывания триггера с заданным послетриггерным объёмом. `[N]`

4.3.3. Наибольший объём захвата в памяти ДОЛЖЕН ограничиваться `MAX_CAPTURE_BYTES = 64 МБ` (64 М
отсчётов); при необходимости больше захват ДОЛЖЕН писаться в файл потоком (п. 7.3.2). `[N]`

4.3.4. Каналы МОГУТ отключаться пользователем; отключённые каналы не показываются и не
экспортируются, но поток с прибора остаётся 8-битным. `[N]`

### 4.4. Триггер

4.4.1. Триггер ДОЛЖЕН задаваться по каждому каналу одним из условий: `0`, `1`, фронт `r`, спад `f`,
любой перепад `e`, «не важно»; условия каналов объединяются логическим И. `[N]`

4.4.2. Доля предзаписи ДОЛЖНА задаваться в процентах `0…99`; предзапись берётся из кольцевого
буфера. `[N]`

4.4.3. Отсчёт, на котором выполнилось условие, ДОЛЖЕН становиться нулём времени захвата. `[N]`

4.4.4. Поиск триггера ДОЛЖЕН выполняться не медленнее поступления данных на 24 МГц (п. 8.1.1). `[N]`

### 4.5. Время

4.5.1. Каждый захват ДОЛЖЕН хранить частоту, номер первого отсчёта и время начала в общей шкале
платформы (`elapsedRealtimeNanos`), вычисленное по завершению первой передачи USB за вычетом
длительности её данных. `[N]`

4.5.2. Модуль ДОЛЖЕН поддерживать совмещение с другими приборами по маркеру: пользователь указывает
канал маркера, и фронты на нём публикуются как события с точным временем по частоте анализатора.
`[N]`

## 5. Просмотр и измерения

### 5.1. Пирамида детализации

5.1.1. По мере поступления данных ДОЛЖНА строиться пирамида: на уровне k (k ≥ 1) каждая ячейка
покрывает `16^k` отсчётов и хранит две 8-битные маски — каналы, у которых внутри ячейки были
перепады, и уровни каналов без перепадов. Так ячейка занимает 2 байта, а вся пирамида — около 13 %
объёма захвата. `[N]`

5.1.2. Запрос «состояние каналов для N колонок экрана на интервале [t1, t2]» ДОЛЖЕН отвечать с
уровня пирамиды, где на колонку приходится не больше одной ячейки, без обхода исходных отсчётов.
`[N]`

5.1.3. Память пирамиды НЕ ДОЛЖНА превышать 15 % объёма захвата. `[N]`

### 5.2. Запросы к захвату

5.2.1. Модуль ДОЛЖЕН находить следующий и предыдущий перепад заданного канала от заданного отсчёта,
пропуская ячейки пирамиды без перепадов. `[N]`

5.2.2. Модуль ДОЛЖЕН возвращать уровень канала в заданном отсчёте. `[N]`

### 5.3. Измерения

5.3.1. Для канала на интервале ДОЛЖНЫ вычисляться: число периодов, частота, скважность, длительности
высокого и низкого уровня (минимум, максимум, среднее, джиттер как разность максимума и минимума).
`[N]`

5.3.2. Для двух каналов ДОЛЖНА вычисляться задержка между перепадами (например, NRST → маркер
старта). `[N]`

5.3.3. Каждый результат измерения ДОЛЖЕН содержать погрешность `±1 отсчёт` на каждый перепад,
выраженную в секундах. `[N]`

5.3.4. Курсоры: два курсора с выводом интервала и частоты `1 / интервал`; курсор МОЖЕТ прилипать к
ближайшему перепаду. `[N]`

## 6. Функциональные требования: жизненный цикл и API

### 6.1. Открытие (`open`)

6.1.1. Открытие ДОЛЖНО: (а) проверить разрешение; (б) захватить интерфейс 0; (в) запросить версию;
(г) при отсутствии ответа — загрузить прошивку (п. 3.2) и открыть устройство заново; (д) проверить
версию (п. 3.3.1); (е) определить скорость шины (п. 3.4.1). `[N]`

6.1.2. Если образ прошивки не выбран, открытие ДОЛЖНО завершаться ошибкой «нужна прошивка fx2lafw» с
предложением выбрать файл. `[N]`

6.1.3. Выбранный пользователем образ ДОЛЖЕН копироваться во внутреннее хранилище приложения и
использоваться при следующих подключениях без повторного выбора. `[N]`

### 6.2. Захват (`start`, `stop`)

6.2.1. `start(config)` ДОЛЖЕН принимать частоту, режим (п. 4.3), длину, маску каналов, условия
триггера и долю предзаписи, проверять их и отвергать недопустимые до обращения к прибору. `[N]`

6.2.2. Во время захвата модуль ДОЛЖЕН сообщать прогресс не реже 5 раз в секунду: число отсчётов,
скорость потока, состояние триггера. `[N]`

6.2.3. `stop()` ДОЛЖЕН завершать захват не позднее чем через 200 мс; повторный вызов ДОЛЖЕН быть
безопасным. `[N]`

### 6.3. Закрытие (`close`)

6.3.1. Закрытие ДОЛЖНО останавливать захват, отменять запросы, освобождать интерфейс; повторное
закрытие и закрытие после отключения прибора — без исключений. `[N]`

### 6.4. Ошибки

6.4.1. Ошибки ДОЛЖНЫ передаваться исключением с видом: `USB_IO`, `NO_FIRMWARE`, `BAD_FIRMWARE`,
`FIRMWARE_VERSION`, `RENUMERATION`, `BAD_CONFIG`, `STREAM_STALL`; текст — на русском с действием для
пользователя. `[N]`

### 6.5. Журнал

6.5.1. Управляющие запросы ДОЛЖНЫ записываться в журнал обмена (тип, запрос, `wValue`, `wIndex`,
длина, данные до 16 байт); загрузка прошивки — одной строкой с размером и SHA-256 образа; данные
bulk — сводкой (байт, скорость). `[N]`

## 7. Требования к интерфейсам

### 7.1. Транспорт

7.1.1. Протокольная часть ДОЛЖНА обращаться к USB только через интерфейс транспорта с операциями:

7.1.2. Для тестов ДОЛЖЕН существовать транспорт-имитатор, выдающий заданный поток отсчётов (в том
числе с обрывом) и записывающий управляющие запросы. `[N]`

### 7.2. Декодеры

7.2.1. Модуль ДОЛЖЕН предоставлять декодерам доступ к захвату только для чтения: частота, длина,
уровень канала в отсчёте, поиск перепадов (п. 5.2.1), итератор перепадов канала на интервале. `[N]`

7.2.2. Декодер МОЖЕТ работать во время непрерывного захвата над уже полученной частью данных. `[N]`

### 7.3. Запись

7.3.1. Экспорт в MCAP ДОЛЖЕН писать канал `/<прибор>/logic` со схемой ROS 1
`hwlivetest_msgs/LogicChunk` (`uint64 first_sample`, `float64 samplerate`, `uint8 channel_mask`,
`uint8[] data`), блоками не более 1 МБ, с временем каждого блока по п. 4.5.1, и метаданные: модель,
версия и SHA-256 прошивки, частота, триггер, имена каналов. `[N]`

7.3.2. При записи в файл во время захвата блоки ДОЛЖНЫ писаться потоком без накопления всего захвата
в памяти. `[N]`

7.3.3. Экспорт в VCD ДОЛЖЕН содержать только перепады включённых каналов с шкалой времени, кратной
периоду отсчётов. `[N]`

7.3.4. Экспорт в `.sr` ДОЛЖЕН создавать архив, который открывается PulseView: метаданные (частота,
имена каналов, размер отсчёта 1 байт) и данные. Формат реализуется по описанию, без кода libsigrok.
`[N]`

### 7.4. Реестр приборов

7.4.1. Модуль ДОЛЖЕН сообщать реестру приборов модель, `deviceName`, скорость шины, версию прошивки
и публикуемые потоки (`/<прибор>/logic`, события маркера). `[N]`

## 11. Допущения и открытые вопросы

### 11.1. Допущения

11.1.1. WeAct LogicAnalyzerV1 без прошивки появляется как `0925:3881` и после загрузки fx2lafw
(`fx2lafw-saleae-logic.fw`) сохраняет VID:PID. Затрагивает п. 3.1.1, 3.1.3.

11.1.2. Константы протокола fx2lafw (`0xB0`–`0xB2`, флаги START, `MAX_DELAY = 1536`) соответствуют
прошивке версии 1.x; сверяются наблюдением обмена PulseView с прибором (вопрос 11.2.3). Затрагивает
разделы 3.3, приложение C.

11.1.3. Телефон пользователя поддерживает USB 2.0 HS в режиме хоста. Затрагивает п. 8.1.1.

## Приложение B. Соглашение о ссылках на ТЗ из кода

B.1. Ссылка на требование оформляется однострочным комментарием рядом с реализацией:
`// ТЗ ЛА 3.3.4`. Для нескольких требований — перечисление через запятую:
`// ТЗ ЛА 4.2.1, 4.2.2`.

B.2. Для тестов используется идентификатор тест-кейса и номера проверяемых требований, например:
`// TC-07: ТЗ ЛА 3.3.3, 3.3.4`.

B.3. Пример:

```kotlin
// ТЗ ЛА 3.3.4: опора 48 МГц, если делится нацело и делитель не больше MAX_DELAY.
if (48_000_000 % rate == 0 && 48_000_000 / rate - 1 <= MAX_DELAY) return Start(FLAG_48MHZ, 48_000_000 / rate - 1)
```

B.4. При удалении требования из документа его номер сохраняется с пометкой «(исключено)» (п. 1.6.2);
комментарий в коде удаляется вместе с реализацией.
