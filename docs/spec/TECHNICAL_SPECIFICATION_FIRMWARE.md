## 1. Введение

### 1.1. Назначение документа

1.1.1. Документ определяет требования к модулю прошивки: резервная копия Flash в Intel HEX, сверка с
HEX, план операции, стирание секторов и полное стирание, прошивка с проверкой, запуск, история
операций — для STM32F4 и STM32F1 через ST-Link с телефона.

1.1.2. Документ является основой для реализации и верификации кода: каждое требование имеет
уникальный номер, на который ссылаются комментарии в коде, тесты и матрица прослеживаемости
(раздел 9).

### 1.2. Область применения

1.2.1. Требования применимы к модулю `firmware` (Kotlin/JVM: HEX, план, алгоритмы контроллеров
Flash, сверка) и к экрану «Прошивка» приложения в части подтверждений и истории.

1.2.2. Документ не описывает протокол ST-Link и команды записи (ТЗ ST-Link 2.0, пункты 3.2.4 и
5.11):
модуль прошивки пользуется ими через интерфейсы `DebugMemory` и `TargetWrite`.

### 1.3. Метод формирования

1.3.1. Резервная копия и сверка восстановлены по коду и проверены на оборудовании (маркер `[R]`).
Прошивка и стирание — новые требования (`[N]`). Регистры контроллеров Flash взяты из reference
manual RM0090, RM0368, RM0383 (F4) и RM0008, PM0075 (F1); код OpenOCD не используется.

1.3.2. Целевой реализацией считается код ветки `main` с доработками по этому документу. В случае
расхождения между этим документом и кодом расхождение считается дефектом одного из них и
разрешается пересмотром ревизии документа.

### 1.4. Термины и сокращения

| Термин | Определение |
| :--- | :--- |
| Цель | Микроконтроллер, подключённый к ST-Link. |
| Образ | Содержимое HEX: участки (адрес, данные). |
| Сектор, страница | Единица стирания Flash: сектор у F4 (16–128 КБ), страница у F1 (1 или 2 КБ). |
| План | Расчёт операции без обращения к цели: секторы, объём, время, проверки. |
| Режим «Изменение цели» | Режим эксперта, в котором разрешены команды записи (ТЗ ST-Link, пункт 5.11.1). |
| RDP | Защита Flash от чтения (Read Protection). |
| WRP | Защита секторов от записи (Write Protection). |
| PSIZE | Ширина записи в контроллере Flash F4 (8, 16, 32 бит). |

## 2. Общее описание

### 2.1. Контекст

2.1.1. Пользователь подключает ST-Link с платой к телефону, выбирает файл HEX и выполняет действие:
план, резервная копия, сверка, стирание или прошивка. Чтение (резервная копия, сверка, план)
доступно всегда; стирание и прошивка — только в режиме «Изменение цели».

### 2.2. Функции

2.2.1. Резервная копия Flash в Intel HEX с SHA-256 (аналог `backup`).

2.2.2. Сверка Flash с HEX только по диапазонам HEX (аналог `check`).

2.2.3. План операции без обращения к цели (аналог `-DryRun`).

2.2.4. Стирание секторов и полное стирание (аналог `erase`).

2.2.5. Прошивка: стирание нужных секторов, запись, сверка, запуск (аналог `flash`).

2.2.6. История операций и отчёт (аналог `.history` и `report.html`).

2.2.7. Файл ELF как источник образа и таблицы сигналов для чтения на ходу (аналог
`resolve_addresses.py` из mcu_power_board, без GDB). (р.1.4)

### 2.3. Роли и потребители

| Роль | Взаимодействие |
| :--- | :--- |
| Экран «Прошивка» | Выбор файла, план, подтверждения, прогресс, результат, история. |
| Модуль ST-Link | Чтение (`DebugMemory`), запись и управление ядром (`TargetWrite`). |
| Опознание цели | Семейство, DEV_ID, размер Flash, напряжение (ТЗ ST-Link, раздел 4). |

### 2.4. Границы

2.4.1. Вне области ТЗ: option bytes (изменение RDP, WRP, BOR), снятие защиты, OTP, EEPROM-эмуляция,
загрузчик в ОЗУ цели (этап 6 плана), семейства кроме F4 и F1 (этап 7), двухбанковая F1 XL-density.

### 2.5. Ограничения платформы

2.5.1. Модуль `firmware` — Kotlin/JVM; из модулей проекта зависит только от `stlink` (р.1.1);
алгоритмы проверяются на JVM моделью контроллера Flash.

2.5.2. Доступ к цели — только через ST-Link (ТЗ ST-Link 2.0).

## 3. Модель защиты

3.1.1. Стирание и прошивка ДОЛЖНЫ быть доступны только в режиме эксперта при включённом режиме
«Изменение цели». Режим ДОЛЖЕН быть выключен по умолчанию и выключаться при каждом запуске
приложения. `[N]`

3.1.2. Каждое стирание и каждая прошивка ДОЛЖНЫ подтверждаться диалогом, в котором показаны:
опознанный MCU и размер Flash, адаптер, файл HEX (имя, размер, SHA-256), секторы для стирания, что
будет потеряно вне HEX в этих секторах, действие после прошивки. `[N]`

3.1.3. Полное стирание ДОЛЖНО требовать двойного подтверждения: второе — вводом слова `СТЕРЕТЬ`.
`[N]`

3.1.4. Операция ДОЛЖНА отклоняться без обращения к цели, если: цель не опознана; семейство не
поддерживается; хотя бы один байт HEX вне Flash цели; RDP ≠ уровень 0; затронутый сектор защищён
WRP; напряжение цели ниже `MIN_VOLTAGE_V = 1,8` В. `[N]`

3.1.5. Перед прошивкой ДОЛЖНА сниматься резервная копия тех секторов или страниц, которые будут
стёрты по плану (п. 5.1.2), в папку приложения; остальная Flash не меняется и в копию не входит.
Пользователь МОЖЕТ отключить копию в настройках, тогда диалог п. 3.1.2 ДОЛЖЕН это показывать.
Копия всей Flash снимается отдельной командой (п. 5.2). На время копии ядро ДОЛЖНО
останавливаться; если операция прервана до стирания, ядро ДОЛЖНО быть запущено снова. Причина:
работающая цель в режиме сна отвечает WAIT, и чтение идёт в десятки раз медленнее. `[N]` (р.1.3)

3.1.6. Модуль НЕ ДОЛЖЕН записывать option bytes и регистры OPTCR (F4) / OPTKEYR, OBR, WRPR (F1).
`[N]`

3.1.7. На время стирания и записи модуль ДОЛЖЕН останавливать сторожевые таймеры при остановленном
ядре (биты DBG_IWDG_STOP и DBG_WWDG_STOP в DBGMCU) и восстанавливать прежнее значение после
операции. Причина: IWDG, запущенный программой, иначе сбросит цель посреди стирания. `[N]`

3.1.8. После операции контроллер Flash ДОЛЖЕН быть заблокирован (бит LOCK) при любом исходе, если
связь с целью сохранилась. `[N]`

## 4. Контроллеры Flash

### 4.1. Общее

4.1.1. Семейство ДОЛЖНО определяться по DEV_ID опознания: F1 — `0x410`, `0x412`, `0x414`; F4 —
`0x413`, `0x419`, `0x423`, `0x431`, `0x433`. Карта секторов или страниц — по приложению C. `[N]`

4.1.2. Разблокировка ДОЛЖНА выполняться записью ключей `0x45670123`, `0xCDEF89AB` в KEYR;
неудачная разблокировка (LOCK остаётся 1) — ошибка без попыток стирания. `[N]`

4.1.3. Перед каждой операцией контроллера ДОЛЖНЫ сбрасываться флаги ошибок в SR, а после —
проверяться BSY и флаги ошибок; ошибка — отказ операции с именем флага. `[N]`

4.1.4. Ожидание BSY ДОЛЖНО быть ограничено таймаутом по п. 4.2.5 и 4.3.4; превышение — ошибка
`FLASH_TIMEOUT`. `[N]`

### 4.2. STM32F4

4.2.1. Регистры: база `0x40023C00`; KEYR `+0x04`, SR `+0x0C` (EOP 0, OPERR 1, WRPERR 4, PGAERR 5,
PGPERR 6, PGSERR 7, BSY 16), CR `+0x10` (PG 0, SER 1, MER 2, SNB 3–6 или 3–7 у F42x, PSIZE 8–9,
MER1 15, STRT 16, LOCK 31). `[N]`

4.2.2. PSIZE ДОЛЖЕН выбираться по напряжению цели: ≥ 2,7 В — 32 бит; 2,1–2,7 В — 16 бит; ниже —
8 бит. Если напряжение не измеряется, ДОЛЖНО использоваться 16 бит, с предупреждением. `[N]`

4.2.3. Стирание сектора: CR = SER | SNB(n) | PSIZE, затем STRT; для секторов второго банка F42x
(12–23) SNB = `0x10 + (n − 12)`. Полное стирание: MER (и MER1 для двух банков F42x) | PSIZE, затем
STRT. `[N]`

4.2.4. Запись: CR = PG | PSIZE, затем данные блоками по `F4_CHUNK_BYTES = 256` байт командой записи
шириной PSIZE (WRITEMEM_32BIT или WRITEMEM_16BIT/8BIT), после каждого блока — ожидание BSY и
проверка
ошибок; затем PG = 0. `[N]`

4.2.5. Таймауты F4: сектор — `F4_SECTOR_TIMEOUT_MS = 4000` мс; полное стирание —
`F4_MASS_TIMEOUT_MS = 40000` мс; блок записи — 100 мс. `[N]`

### 4.3. STM32F1

4.3.1. Регистры: база `0x40022000`; KEYR `+0x04`, SR `+0x0C` (BSY 0, PGERR 2, WRPRTERR 4, EOP 5),
CR `+0x10` (PG 0, PER 1, MER 2, STRT 6, LOCK 7), AR `+0x14`. `[N]`

4.3.2. Стирание страницы: CR = PER, AR = адрес страницы, затем STRT. Полное стирание: CR = MER,
затем
STRT. `[N]`

4.3.3. Запись ДОЛЖНА идти полусловами: CR = PG, затем данные блоками по `F1_CHUNK_BYTES = 256` байт
командой WRITEMEM_16BIT (адаптер J26+ или V3, ТЗ ST-Link пункт 3.2.4), после каждого блока —
ожидание BSY и проверка PGERR и WRPRTERR. На адаптере без WRITEMEM_16BIT прошивка F1 ДОЛЖНА
отклоняться с просьбой обновить прошивку адаптера (вопрос 10.2.1). `[N]`

4.3.4. Таймауты F1: страница и полное стирание — `F1_ERASE_TIMEOUT_MS = 500` мс; блок записи —
100 мс. `[N]`

## 5. Функциональные требования: операции

### 5.1. План (`plan`)

5.1.1. План ДОЛЖЕН строиться без обращения к цели по образу и опознанию: секторы для стирания,
объём записи, оценка времени, SHA-256 образа, результат проверок п. 3.1.4, которые можно выполнить
без цели. `[N]`

5.1.2. Секторы для стирания ДОЛЖНЫ быть ровно теми, что пересекаются с участками образа. План ДОЛЖЕН
показывать объём данных вне образа в этих секторах, который будет потерян. `[N]`

5.1.3. Если рядом с образом пользователь указал файл `*.sha256` или ввёл ожидаемую сумму, план
ДОЛЖЕН
сравнить её с SHA-256 образа; несовпадение блокирует прошивку. `[N]`

### 5.2. Резервная копия (`backup`)

5.2.1. Резервная копия ДОЛЖНА читать Flash блоками по 1 КБ (ТЗ ST-Link, пункт 3.6.2) и сохранять
Intel
HEX с SHA-256 данных в журнале. `[R]`

5.2.2. Хвост из `0xFF` ДОЛЖЕН обрезаться с выравниванием на 16 байт. `[R]`

5.2.3. Чтение ДОЛЖНО отменяться пользователем между блоками. `[R]`

5.2.4. Самостоятельная копия всей Flash ДОЛЖНА запускаться с экрана «Прошивка» и
сохраняться в выбранный через Android файл HEX. Операция не требует режима изменения
цели, не останавливает ядро, показывает прогресс и поддерживает отмену между блоками.
При неизвестном размере Flash или отсутствии подключения выдаётся объяснение отказа.
Пустая Flash сохраняется как HEX с записью конца файла; при отмене выбранный документ
может остаться пустым. Состояние выполняемой операции сохраняется при повороте. (р.1.6) `[N]`

### 5.3. Сверка (`check`)

5.3.1. Сверка ДОЛЖНА читать только диапазоны образа и сообщать число несовпадений и первые адреса.
`[R]`

5.3.2. Сверка НЕ ДОЛЖНА останавливать и сбрасывать ядро. `[R]`

### 5.4. Стирание (`erase`)

5.4.1. Стирание ДОЛЖНО выполнять шаги: (а) проверки п. 3.1.4; (б) подтверждение п. 3.1.2 или
п. 3.1.3; (в) сброс с остановкой (ТЗ ST-Link, пункт 5.11.5); (г) остановка сторожевых таймеров по
п. 3.1.7; (д) разблокировка; (е) стирание; (ж) блокировка; (з) восстановление DBGMCU. `[N]`

5.4.2. После стирания модуль ДОЛЖЕН проверить чтением, что стёртые секторы содержат `0xFF` (по
`ERASE_SAMPLE_BYTES = 1024` байт в начале и конце каждого сектора). `[N]`

5.4.3. Ядро после стирания ДОЛЖНО оставаться остановленным. `[N]`

### 5.5. Прошивка (`flash`)

5.5.1. Прошивка ДОЛЖНА выполнять шаги: (а) план и проверки (п. 5.1, 3.1.4); (б) подтверждение
(п. 3.1.2); (в) резервная копия (п. 3.1.5); (г) сброс с остановкой; (д) остановка сторожевых
таймеров; (е) разблокировка; (ж) стирание секторов плана; (з) запись участков образа; (и)
блокировка; (к) сверка по п. 5.3.1; (л) восстановление DBGMCU; (м) действие после прошивки
(п. 5.6). `[N]`

5.5.2. Прогресс ДОЛЖЕН показываться по шагам и в байтах не реже 4 раз в секунду. `[N]`

5.5.3. Отмена ДОЛЖНА быть возможна только между секторами при стирании и между блоками при записи;
после отмены контроллер блокируется, ядро остаётся остановленным, а результат помечается
«прошивка не завершена». `[N]`

5.5.4. Отказ команды записи с WAIT НЕ ДОЛЖЕН повторяться автоматически (повторная запись во
Flash даёт ошибку программирования): операция прерывается с результатом «прошивка не завершена».
`[N]`

5.5.5. Если связь с адаптером потеряна во время стирания или записи, результат ДОЛЖЕН быть «прошивка
не завершена» с подсказкой: переподключить и прошить заново; при недоступном ядре — подключиться
под сбросом (NRST). `[N]`

5.5.6. Ошибка сверки после записи ДОЛЖНА давать результат «ошибка сверки» с первыми адресами, ядро
не запускается. `[N]`

### 5.6. Действие после прошивки

5.6.1. По умолчанию после успешной сверки ДОЛЖЕН выполняться сброс с запуском (ТЗ ST-Link,
пункт 5.11.4). Пользователь МОЖЕТ выбрать «оставить остановленным». `[N]`

5.6.2. После запуска приложение СЛЕДУЕТ предлагать «ПУСК» для проверки, что новая прошивка работает.
`[N]`

### 5.7. История и отчёт

5.7.1. Каждая операция ДОЛЖНА добавлять запись в историю (файл `history.jsonl` в папке приложения):
время, действие, адаптер и прошивка адаптера, MCU (без UID), файл и SHA-256, секторы, длительность,
результат, текст ошибки. `[N]`

5.7.2. Отчёт об операции ДОЛЖЕН сохраняться текстом и отправляться кнопкой «Отправить». Отчёт
ДОЛЖЕН содержать длительность каждого шага со скоростью и статистику обмена с адаптером (число
передач USB, среднее и наибольшее время). `[N]` (р.1.2)

5.7.3. История ДОЛЖНА показываться на экране «Прошивка», новые сверху, и очищаться только по
команде пользователя. `[N]`

5.7.4. Каждое действие пользователя на экранах изменения цели и каждый ответ программы ДОЛЖНЫ
записываться в журнал сеанса строками `# пользователь: …` и `# программа: …`; последние строки
диалога ДОЛЖНЫ показываться на экране «Прошивка». Это модель будущего экрана-диалога. `[N]` (р.1.4)

### 5.8. Ошибки

5.8.1. Ошибки модуля ДОЛЖНЫ иметь виды: `REFUSED` (проверки п. 3.1.4, с причиной), `LOCKED`
(разблокировка не удалась), `FLASH_ERROR` (флаг SR), `FLASH_TIMEOUT`, `VERIFY_FAILED`,
`INCOMPLETE` (отмена, WAIT, потеря связи), `CANCELLED` (до начала изменений). `[N]`

### 5.9. ELF и таблица сигналов (р.1.4)

5.9.1. Файл ELF32 (ARM, little-endian) ДОЛЖЕН приниматься наравне с Intel HEX. Образ для прошивки —
загружаемые сегменты (PT_LOAD) с данными в файле по физическим адресам (LMA), смежные сливаются;
перекрытие сегментов — ошибка формата. `[N]`

5.9.2. Из отладочной информации DWARF версий 2–5 (32-битный формат) ДОЛЖНА строиться таблица
сигналов: переменные с постоянным адресом (DW_OP_addr, DW_OP_addrx), поля структур и объединений,
элементы массивов (до `MAX_ARRAY = 8` на измерение) с именем вида `sensors.cached_data.voltage_batt`
и типом. Битовые поля пропускаются. В таблицу попадают значения в ОЗУ размером 1, 2 и 4 байта,
не пересекающие границу слова; 1- и 2-байтовые — с адресом слова, сдвигом и маской. `[N]`

5.9.3. Таблица ДОЛЖНА записываться в формате `addresses.json` schema 2 (контракт mcu_power_board)
с ключами `elf_sha256` и `image_sha256` (SHA-256 образа по п. 5.9.1) и подключаться к полям
приложения только для цели, Flash которой совпадает с образом: после сверки без расхождений или
после успешной прошивки этим ELF. Без совпадения таблица не подключается, и журнал (п. 5.7.4) это
сообщает. `[N]`

5.9.4. Если в ELF нет отладочной информации, образ ДОЛЖЕН прошиваться, а таблица — быть пустой
с предупреждением в журнале. `[N]`

5.9.5. Таблица из ELF ДОЛЖНА включать `source_type` (имя типа DWARF), `size_bits` и
`source_file` (п. 5.9.6). Экран показывает исходный тип вместо транспортного `kind`.
Знаковые значения 1 и 2 байта передаются как `kind=int32`, `message=std_msgs/Int32`:
после маски и сдвига декодер расширяет знак с 8/16 бит. Старые таблицы без новых ключей
читаются по прежним правилам; `description` используется как запасная подпись типа. (р.1.5) `[N]`

5.9.6. Сигнал из ELF ДОЛЖЕН хранить путь единицы компиляции (CU, `DW_AT_name`).
Это источник единицы трансляции, а не гарантированное место объявления в заголовке.
Каталог сборочной машины удаляется; для внешнего абсолютного пути остаётся имя файла.
Топик имеет вид `/elf/<путь CU>/<путь переменной>`; символы, кроме ASCII-букв, цифр,
подчёркивания и разделителей, заменяются на `_`. При совпадении топиков добавляется адрес
`_at_<hex>`. При отсутствии CU остаётся `/elf/<путь переменной>`. (р.1.5) `[N]`

5.9.7. Экран эксперта ДОЛЖЕН поддерживать поиск по топику, выражению, исходнику, типу
и адресу, фильтр типа, сворачиваемые группы по CU, родительскому топику или типу и режим
без групп. Показываются число найденных и общее число сигналов. Фильтры не изменяют
таблицу, опрос и имена топиков MCAP. Импорт готового `addresses.json` заменяет активную
таблицу и сохраняет его топики, выражения, маски, границы и типы сообщений; выражения
не исполняются. Как и ранее, соответствие вручную выбранной таблицы прошивке проверяет
пользователь; правило п. 5.9.3 относится к автоматическому подключению таблицы ELF.
Для старых таблиц без CU доступна группировка по топику. (р.1.5) `[N]`

5.9.8. Экран эксперта ДОЛЖЕН использовать Compose Material 3: версия и часы в шапке,
поиск и подключение ST-Link, сведения адаптера и MCU, чтение слова, ленивый список
сигналов со значениями и предупреждениями, переход к графику, меню простого режима,
цели, прошивки и сведений о программе. Журнал открывается диалогом: действия и ответы
различаются, обмен USB скрыт переключателем, полный журнал копируется независимо
от фильтра. Поиск, группировка, фильтр типа, адрес и прокрутка сохраняются при повороте;
опрос прекращается при уходе и возобновляется при возвращении. Операции изменения
цели на этот экран не добавляются. (р.1.5) `[N]`

5.9.9. Часы и очередные показания НЕ ДОЛЖНЫ сбрасывать позицию прокрутки или закрывать
меню эксперта. Меню ДОЛЖНО находиться в неподвижной шапке вне списка сигналов.
Обновление показаний ограничивается строками сигналов; область значения сохраняет
высоту при появлении ошибки или выхода за границы. (р.1.6) `[N]`

### 5.10. Простой режим (р.1.6)

5.10.1. Простой режим ДОЛЖЕН использовать Compose Material 3 с общей темой, часами и
версией. Кнопка «ПУСК» подключает адаптер и выполняет прежние эвристики диагностики;
во время проверки кнопка «СТОП» запрашивает отмену. Итог и раскрываемые карточки содержат
все наблюдения, подробности и уровни оценки прежнего отчёта. Отчёт вместе с полным
журналом можно скопировать. Эвристики и команды обмена не изменяются. (р.1.6) `[N]`

5.10.2. Поворот экрана НЕ ДОЛЖЕН запускать диагностику повторно или терять её прогресс.
До завершения операции переходы на экраны обмена недоступны; возврат запрашивает отмену.
При ошибке сохраняется её сообщение, при отмене предыдущий отчёт не выдаётся за новый.
Завершение владельца состояния запрашивает отмену незавершённой операции. (р.1.6) `[N]`

5.10.3. Копия и сверка ДОЛЖНЫ быть убраны из реализации простого режима и доступны через
экран «Прошивка». При входе из простого режима экран открывается только для чтения,
без элементов изменения цели, даже если ранее эксперт включил разрешение записи.
Сверка использует существующий путь HEX/ELF (п. 5.3, 5.9); выбранный файл и выполняемая
операция сохраняются при повороте. Изменение цели доступно через режим эксперта по
существующим правилам раздела 3. (р.1.6) `[N]`

### 5.11. График на Compose (р.1.7)

5.11.1. Экран ДОЛЖЕН использовать Compose Canvas без Android View. Сохраняются до шести
каналов в порядке выбора, выбор активного канала нажатием на легенду или статистику,
крупное значение, окна 30 с / 1 мин / 5 мин, автоматические или общие/отдельные шкалы Y
с гистерезисом, средние у осей, разрывы линий при пропусках свыше 1 с. (р.1.7) [N]

5.11.2. Пауза ДОЛЖНА фиксировать правую границу графика; последующие отсчёты не входят в
его диапазоны и статистику. Опрос и запись при этом продолжаются. Выбор каналов,
активный канал, масштаб и пауза ДОЛЖНЫ переживать поворот экрана. (р.1.7) [N]

5.11.3. Запись MCAP выбранных полей, экспорт последних пяти минут, выбор папки SAF и
отправка файла ДОЛЖНЫ сохраняться. Во время записи выбор каналов заблокирован. Запись
переживает поворот, при выходе с графика файл закрывается. Ожидающее действие после
выбора папки и результат записи сохраняются при повороте. (р.1.7) [N]

5.11.4. Отрисовка графика ДОЛЖНА быть ограничена его прямоугольником и НЕ ДОЛЖНА
перекрашивать соседние элементы. Фон, подписи и сетка следуют теме приложения. В альбомной
ориентации управление прокручивается слева, график занимает высоту справа и остаётся видимым.
В портретной ориентации крупное значение и выбор окна находятся над графиком. (р.1.8) [N]

### 5.12. Повторное USB-подключение (р.1.7)

5.12.1. Системное USB_DEVICE_ATTACHED НЕ ДОЛЖНО запускать простой режим или эксперта
поверх уже открытого экрана. Отдельная невидимая Activity обновляет выбор адаптера и
завершается. Главный экран запускается только при отсутствии существующей задачи. (р.1.7) [N]

5.12.2. Отключение USB ДОЛЖНО завершать соединение и очищать сведения адаптера и MCU;
повторное обнаружение сообщает о необходимости подключения. Оно НЕ ДОЛЖНО автоматически
повторять диагностику, прошивку или другую операцию. (р.1.7) [N]

### 5.13. Общая навигация и журнал (р.1.8)

5.13.1. Все рабочие экраны ДОЛЖНЫ использовать общую шапку с часами и версией, меню
«Журнал» / «О программе» и действиями текущего экрана. Текущий информационный экран
исключается из меню; повторное открытие уже существующего возвращает его из стека.
Стрелка и системный «Назад» ДОЛЖНЫ вызывать один обработчик с сохранением подтверждений
выхода и отмены операции. Переходы к информационным экранам заблокированы во время
операций и записи MCAP. Возможность записи в цель из простого режима не добавляется. (р.1.8) [N]

5.13.2. Журнал ДОЛЖЕН быть отдельным Compose-экраном, показывающим последние 300 строк
как диалог пользователя и программы. Обмен USB скрывается переключателем; копирование
сохраняет весь журнал сеанса. Очистка требует подтверждения. Обновление выполняется
только при видимом журнале, идентификаторы строк сохраняются при добавлении и вытеснении
старых записей, положение чтения не сбрасывается из-за обновления часов. (р.1.8) [N]

5.13.3. Неиспользуемые XML простого режима и эксперта и старый FieldRow ДОЛЖНЫ быть
удалены. Общая тема приложения — без ActionBar, шапку рисует Compose. Отложенный
логический анализатор сохраняет собственные XML, стили, ClockActivity и LogPresenter
в отдельной LegacyLogicTheme и НЕ появляется в рабочем меню. (р.1.8) [N]

### 5.14. Общее состояние подключения (р.1.9)

5.14.1. Экраны ДОЛЖНЫ использовать одну сессию USB → SWD → MCU. Повторный запрос
к тому же доступному адаптеру НЕ ДОЛЖЕН закрывать действующий транспорт и повторять
опознание. Отключение, смена адаптера или потеря разрешения исключают повторное
использование старого соединения. Неудачное подключение не кешируется. [N]

5.14.2. Статус маршрута, сведения об адаптере и MCU, режим изменения цели и последнее
прочитанное состояние ядра ДОЛЖНЫ быть общими. «Цель» и «Прошивка» подхватывают их
при возвращении на экран и изменении сессии. Разрешение изменения цели отзывается при
отключении и смене адаптера. Состояние ядра перечитывается при входе на эти экраны. [N]

### 5.15. Равноправные страницы эксперта (р.1.9)

5.15.1. «Сигналы», «Цель», «Прошивка», «Журнал» ДОЛЖНЫ переключаться вкладками
и горизонтальным свайпом с переходом по кругу. Выбранный файл прошивки и состояние
экранов сохраняются при переключении. «Назад» возвращает в простой режим.
График остаётся отдельным экраном: его жесты управляют графиком. [N]

5.15.2. Во время операции переходы блокируются. Уход с остановленной целью сохраняет
подтверждение запуска; при ошибке запуска приложение остаётся на экране и показывает
ошибку. Переход не выдаёт разрешения на изменение цели. Инструменты прошивки,
открытые из простого режима, остаются только для чтения. [N]

5.15.3. Кнопки в одном ряду ДОЛЖНЫ иметь одинаковую высоту при переносе подписи. [N]

### 5.16. Компактные сведения и направление переходов (р.1.10)

5.16.1. Блоки «Адаптер», «Микроконтроллер», «Чтение слова» ДОЛЖНЫ начинаться
свёрнутыми. Нажатие заголовка переключает раскрытие; выбор сохраняется при повороте
и возврате на страницу. Заголовок доступен как кнопка со статусом раскрытия. [N]

5.16.2. При свайпе влево текущая страница уходит влево, следующая входит справа;
при свайпе вправо — наоборот. Направление сохраняется на границе циклического
списка и после подтверждения выхода с остановленным ядром. [N]

### 5.17. История графиков (р.1.10)

5.17.1. Ряды НЕ ДОЛЖНЫ смешивать данные разных подключений или данные до и после
команд изменения цели. При закрытии подключения и перед выполнением подтверждённых
команд управления ядром, прошивки или стирания история очищается для всех каналов.
Обычная смена страницы, поворот и выбор окна историю не очищают. [N]

5.17.2. Пятиминутное окно ДОЛЖНО сохранять хронологический порядок после оборота
кольцевого буфера. При 20 Гц ёмкости достаточно для пяти минут. Большие конечные
значения не скрываются произвольным фильтром; действуют границы из таблицы полей. [N]

5.17.3. На графике доступна ручная очистка истории для начала нового интервала.
Она недоступна во время записи MCAP; сохранённые записи не удаляются. [N]

### 5.18. Настройки и маршруты инженера (р.1.11)

5.18.1. Настройка «Отладочные сведения» ДОЛЖНА быть выключена по умолчанию и
сохраняться между запусками. Адреса, выражения ELF, исходники, регистры и чтение
слова показываются только при её включении. Предупреждения чтения и границ значений
не скрываются. Совпадающие короткие имена различаются полным путём сигнала. [N]

5.18.2. Основное подключение ДОЛЖНО иметь одну кнопку «Подключить», видимую при
отсутствии соединения. Отдельная кнопка поиска исключается; поиск входит в подключение.
Простой режим использует компактную кнопку проверки и строки результатов; проблемы
раскрываются исходно, успешные пункты — по нажатию. [N]

5.18.3. «Быстрые действия» включаются отдельным подтверждением при действующем
подключении и разрешении изменения цели. Только halt/go/reset/resetHalt могут
выполняться без повторного диалога. Прошивка, стирание, NRST и вопрос о запуске
при уходе сохраняют подтверждения. Неизвестные команды подтверждаются всегда. [N]

5.18.4. Быстрый режим НЕ сохраняется на диск и сбрасывается при закрытии подключения,
смене/отключении адаптера, выключении изменения цели и новом процессе. Режим явно
отображается в общей строке состояния. Настройка не выдаёт WritePermit. [N]

5.18.5. Настройки содержат выбор резервной копии перед прошивкой; изменение подхватывается
экраном прошивки при возвращении. По умолчанию копия включена. [N]

## Приложение B. Соглашение о ссылках на ТЗ из кода

B.1. Ссылка на требование оформляется однострочным комментарием рядом с реализацией:
`// ТЗ прошивки 4.2.3`. Для нескольких требований — перечисление через запятую.

B.2. Для тестов используется идентификатор тест-кейса и номера проверяемых требований, например:
`// TC-06: ТЗ прошивки 4.2.3`.

B.3. Пример:

```kotlin
// ТЗ прошивки 4.2.3: секторы второго банка F42x кодируются как 0x10 + (n - 12).
val snb = if (n < 12) n else 0x10 + (n - 12)
```

B.4. При удалении требования из документа его номер сохраняется с пометкой «(исключено)» (п. 1.6.2);
комментарий в коде удаляется вместе с реализацией.
