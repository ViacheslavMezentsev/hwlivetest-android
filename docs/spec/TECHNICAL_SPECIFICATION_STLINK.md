## 1. Введение

### 1.1. Назначение документа

1.1.1. Документ определяет требования к модулю поддержки ST-Link: поиск адаптера на шине USB,
подключение по SWD, чтение памяти и регистров отладки работающего микроконтроллера Cortex-M,
опознание микроконтроллера и — только с разрешения (п. 5.11) — запись памяти и регистров отладки,
остановку, запуск и сброс ядра для прошивки и управления в режиме эксперта. (р.2.0)

1.1.2. Документ является основой для реализации и верификации кода: каждое требование имеет
уникальный номер, на который ссылаются комментарии в коде, тесты и матрица прослеживаемости (раздел
9).

### 1.2. Область применения

1.2.1. Требования применимы к модулю `stlink` (протокол, опознание) и к части модуля `usb`, которая
относится к ST-Link (поиск, разрешение, транспорт).

1.2.2. Документ не описывает эвристики «ПУСК» (`diag`), разбор полей и опрос (`telemetry`), запись
MCAP (`recorder`), резервное копирование Flash (`firmware`) и экраны (`app`). Их взаимодействие с
модулем описано в разделе 6.

### 1.3. Метод формирования

1.3.1. Требования восстановлены по коду и тестам модулей `stlink` и `usb`, по журналам обмена с
адаптерами ST-Link/V2 (клон и встроенный в STM32F429I-DISCO) и ST-Link/V2-1 (встроенный в
NUCLEO-F030R8 и отдельный), с платами STM32F103, STM32F401, STM32F411, STM32F030, STM32F429 и
AT32F403A. Новые требования (маркер `[N]`) вводят белый список команд и работу с несколькими
адаптерами.

1.3.2. Целевой реализацией считается код ветки `main` с поправками, перечисленными в приложении D. В
случае расхождения между этим документом и кодом расхождение считается дефектом одного из них и
разрешается пересмотром ревизии документа.

### 1.4. Термины и сокращения

| Термин | Определение |
| :--- | :--- |
| Адаптер | Отладчик ST-Link/V2, V2-1 или V3, подключённый к телефону по USB. |
| Цель | Микроконтроллер Cortex-M, подключённый к адаптеру по SWD. |
| SWD | Serial Wire Debug — двухпроводный отладочный интерфейс Arm. |
| DP, AP, MEM-AP | Debug Port, Access Port, Memory Access Port по ADIv5. |
| API v2 | Набор команд ST-Link для прошивок V2 J13+ и V3. |
| Прошивка J | Номер версии JTAG/SWD-части прошивки адаптера (`V2J37S7`). |
| WAIT | Ответ DP или AP «занят, повторите». |
| Журнал обмена | Текстовая запись команд и ответов в формате `> f1 80` / `< 29 47 …`. |
| Составное устройство | Устройство USB с несколькими интерфейсами (у V2-1: отладка, VCP, накопитель). |

## 2. Общее описание

### 2.1. Контекст

2.1.1. Пользователь подключает адаптер ST-Link к телефону через OTG (напрямую или через хаб),
адаптер — к плате по SWD. Модуль находит адаптер, получает разрешение USB, входит в режим SWD и
читает память работающей цели по запросам потребителей: опознания, эвристик «ПУСК», опроса полей,
резервного копирования Flash.

### 2.2. Функции модуля

2.2.1. Поиск известных адаптеров по VID:PID и запрос разрешения USB.

2.2.2. Подключение: версия прошивки адаптера, текущий режим, напряжение цели, вход в SWD, DP IDCODE.

2.2.3. Чтение 32-битного слова, блока слов и регистров AP с повтором при WAIT.

2.2.4. Опознание цели: ядро, производитель, серия STM32 или AT32, размер Flash.

2.2.5. Журнал обмена для диагностики и тестов воспроизведения.

### 2.3. Роли и потребители

| Роль | Взаимодействие |
| :--- | :--- |
| Экраны (`app`) | Поиск, разрешение, подключение, отключение; показ версии, напряжения, опознания. |
| Эвристики (`diag`) | Чтение регистров отладки и периферии через `DebugMemory`. |
| Опрос полей (`telemetry`) | Блочное чтение через `DebugMemory.readBlock`. |
| Резервная копия (`firmware`) | Блочное чтение Flash. |
| Тесты | Транспорт воспроизведения по журналам обмена. |
| Будущий реестр приборов (`instrument`) | Несколько адаптеров одновременно, общий доступ к составному устройству. |

### 2.4. Границы

2.4.1. Вне области ТЗ: алгоритмы программирования Flash (ТЗ прошивки), option bytes и защита Flash
(RDP), пошаговое исполнение и точки останова, трассировка SWO, JTAG, SWIM, обновление прошивки
адаптера, мост VCP (описан в ТЗ USB-UART). (р.2.0)

### 2.5. Ограничения платформы

2.5.1. Протокольная часть (`stlink`) — Kotlin/JVM без зависимостей от Android; транспорт передаётся
ей интерфейсом `StLinkTransport`.

2.5.2. Порядок байтов в командах и ответах — little-endian.

2.5.3. Доступ к USB — только Android USB Host API (`UsbManager`), без root и драйверов ядра.

## 3. Протокол обмена с адаптером

### 3.1. Транспорт

3.1.1. Обмен ДОЛЖЕН выполняться парами «команда — ответ»: команда длиной `CMD_SIZE = 16` байт
передаётся в bulk OUT, ответ фиксированной для команды длины читается из bulk IN. Неиспользуемые
байты команды ДОЛЖНЫ быть нулевыми. `[R]`

3.1.2. Интерфейсом отладки ДОЛЖЕН считаться первый интерфейс класса `0xFF` (vendor specific), у
которого есть bulk OUT и bulk IN; из нескольких точек одного направления ДОЛЖНА выбираться точка с
меньшим адресом. Причина: вторая IN-точка (`0x82`/`0x83`) — трассировка SWO. `[R]`

3.1.3. Ответ ДОЛЖЕН читаться буфером, кратным `maxPacketSize` IN-точки (не менее 64 байт), и
обрезаться до ожидаемой длины. Причина: чтение буфером меньше пакета приводит к переполнению
(babble). `[R]`

3.1.4. Каждая bulk-транзакция ДОЛЖНА ограничиваться таймаутом `USB_TIMEOUT_MS = 1000` мс; превышение
таймаута или отрицательный результат ДОЛЖНЫ завершаться ошибкой вида `USB_IO`. `[R]`

3.1.5. Ответ короче ожидаемой длины ДОЛЖЕН завершаться ошибкой вида `PROTOCOL`. `[R]`

3.1.6. Обращения к закрытому транспорту ДОЛЖНЫ завершаться ошибкой `USB_IO` без обращения к USB.
`[R]`

### 3.2. Белый список команд

3.2.1. Модуль ДОЛЖЕН кодировать только команды двух списков: чтение (таблица п. 3.2.2) и изменение
цели (таблица п. 3.2.4). Команды изменения цели ДОЛЖНЫ кодироваться в отдельном объекте и
отправляться только через интерфейс `TargetWrite` (п. 6.2.3). Команды записи option bytes, стирания
через адаптер, пошагового исполнения и SWIM НЕ ДОЛЖНЫ кодироваться. `[U]` (р.2.0)

3.2.2. Допустимые команды перечислены в таблице ниже. `[R]`

| Команда | Байты | Ответ, байт | Минимальная прошивка | Назначение |
| :--- | :--- | :---: | :---: | :--- |
| GET_VERSION | `F1 80` | 6 | любая | версия, VID:PID |
| GET_VERSION_APIV3 | `FB 80` | 12 | V3 | версия V3 |
| GET_CURRENT_MODE | `F5` | 2 | любая | режим адаптера |
| DFU_EXIT | `F3 07` | 0 | любая | выход из DFU адаптера |
| SWIM_EXIT | `F4 01` | 0 | любая | выход из SWIM |
| DEBUG_EXIT | `F2 21` | 0 | любая | выход из режима отладки адаптера |
| GET_TARGET_VOLTAGE | `F7` | 8 | V2 J13 | напряжение цели |
| DEBUG_APIV2_ENTER (SWD) | `F2 30 A3` | 2 | V2 J13 | вход в SWD |
| READ_IDCODES | `F2 31` | 12 | V2 J13 | DP IDCODE |
| READDEBUGREG | `F2 36` + адрес | 8 | V2 J13 | одно слово памяти |
| READMEM_32BIT | `F2 07` + адрес + длина | длина | V2 J13 | блок памяти |
| GETLASTRWSTATUS | `F2 3B` | 2 | V2 J13 | состояние блока |
| GETLASTRWSTATUS2 | `F2 3E` | 12 | V2 J15, V3 | состояние блока |
| READ_DAP_REG | `F2 45` + порт + регистр | 8 | V2 J24, V3 | регистр DP или AP |

3.2.3. Команда DEBUG_EXIT ДОЛЖНА выводить из режима отладки только адаптер; ядро цели продолжает
работу. Это поведение подтверждается на оборудовании для каждого поколения адаптера. `[R]`

3.2.4. Команды изменения цели перечислены в таблице ниже. `[N]` (р.2.0)

| Команда | Байты | Ответ, байт | Минимальная прошивка | Назначение |
| :--- | :--- | :---: | :---: | :--- |
| WRITEDEBUGREG | `F2 35` + адрес + значение | 2 | V2 J13 | запись одного слова (DHCSR, DEMCR, AIRCR, регистры Flash) |
| WRITEMEM_32BIT | `F2 08` + адрес + длина, затем данные | 0 | V2 J13 | запись блока словами |
| WRITEMEM_16BIT | `F2 48` + адрес + длина, затем данные | 0 | V2 J26, V3 | запись блока полусловами (Flash STM32F1) |
| WRITEMEM_8BIT | `F2 0D` + адрес + длина, затем данные | 0 | V2 J13 | запись до 64 байт побайтно |
| DRIVE_NRST | `F2 3C` + режим (`00` низкий, `01` высокий, `02` импульс) | 2 | V2 J13 | управление выводом NRST |

3.2.5. После каждой команды записи блока ДОЛЖНО запрашиваться состояние (п. 3.4.6), как после чтения
блока (п. 3.6.4); отказ — ошибка `SWD_FAULT` с адресом. `[N]` (р.2.0)

3.2.6. Блок записи ДОЛЖЕН подчиняться тем же ограничениям, что блок чтения (п. 3.6.1, 3.6.2): адрес
выровнен на размер элемента, длина кратна ему, не больше `MAX_BLOCK_BYTES`, без пересечения границы
1 КБ; для `WRITEMEM_8BIT` — не больше `MAX_BYTE_BLOCK = 64` байт. `[N]` (р.2.0)

3.2.7. Остановка, запуск и сброс ядра ДОЛЖНЫ выполняться записью архитектурных регистров Cortex-M
(DHCSR, DEMCR, AIRCR) командой WRITEDEBUGREG, а не устаревшими командами адаптера FORCEDEBUG,
RUNCORE, RESETSYS. Причина: регистры одинаковы на всех адаптерах и прошивках и описаны Arm. `[N]`
(р.2.0)

### 3.3. Коды состояния и повторы

3.3.1. Код `STATUS_OK = 0x80` в первом байте ответа ДОЛЖЕН считаться успехом; любой другой код —
отказом с текстом по приложению C. `[R]`

3.3.2. Коды `0x10` (AP WAIT) и `0x14` (DP WAIT) ДОЛЖНЫ считаться повторяемыми. Чтение слова,
регистра AP или блока при таком коде ДОЛЖНО повторяться не более `WAIT_RETRIES = 5` раз с задержками
1, 2, 4, 8, 16 мс. Причина: цель отвечает WAIT, когда шина занята или ядро спит без включённых
отладочных часов в DBGMCU_CR, а записывать туда модуль не может. `[R]`

3.3.3. Каждый повтор ДОЛЖЕН записываться в журнал обмена строкой-комментарием с номером повтора и
задержкой. `[R]`

3.3.4. Число повторов ДОЛЖНО задаваться при создании сеанса; значение 0 отключает повторы. `[R]`

3.3.5. Если после исчерпания повторов код остаётся WAIT, текст ошибки ДОЛЖЕН содержать число
выполненных повторов. `[R]`

3.3.6. Коды `0x09` и `0x14`–`0x17` при входе в SWD или чтении IDCODE ДОЛЖНЫ сообщаться как ошибка
вида `NO_TARGET` с подсказкой проверить питание платы и провода SWDIO, SWCLK, GND. `[R]`

### 3.4. Версия адаптера

3.4.1. Ответ GET_VERSION ДОЛЖЕН разбираться так: слово из байтов 0–1 (старший первым): биты 15–12 —
поколение, 11–6 — версия J, 5–0 — версия SWIM (у V2) или накопителя (у V2-1); байты 2–3 и 4–5 — VID
и PID (little-endian). `[R]`

3.4.2. Для поколения 3 и выше версия ДОЛЖНА уточняться командой GET_VERSION_APIV3: байты 0–4 —
поколение, SWIM, J, накопитель, мост; байты 8–9 и 10–11 — VID и PID. `[R]`

3.4.3. Метка версии ДОЛЖНА строиться в стиле ST: `V2J37S7`, `V2J37M26`, `V3J7M3B5S1`. `[R]`

3.4.4. Адаптер поколения 1 ДОЛЖЕН отвергаться ошибкой `UNSUPPORTED_ADAPTER`. `[R]`

3.4.5. Адаптер V2 с прошивкой старше `MIN_V2_JTAG = 13` ДОЛЖЕН отвергаться ошибкой `OLD_FIRMWARE` с
предложением обновить прошивку программой STM32CubeProgrammer или ST-LinkUpgrade. `[R]`

3.4.6. Расширенный статус GETLASTRWSTATUS2 ДОЛЖЕН использоваться при прошивке V2 J15+ или V3, иначе
— GETLASTRWSTATUS. `[R]`

3.4.7. Чтение регистров DP и AP командой READ_DAP_REG ДОЛЖНО использоваться только при прошивке V2
J24+ или V3; на более старых прошивках операция ДОЛЖНА возвращать «нет значения», а не ошибку. `[R]`

### 3.5. Напряжение цели

3.5.1. Напряжение ДОЛЖНО вычисляться по ответу GET_TARGET_VOLTAGE как `2 × adc1 × 1,2 / adc0`, где
`adc0` и `adc1` — 32-битные слова по смещениям 0 и 4. При `adc0 = 0` напряжение ДОЛЖНО считаться
неизмеряемым. `[R]`

3.5.2. При напряжении ниже `LOW_VOLTAGE_V = 1,5` В подключение ДОЛЖНО продолжаться, а в
предупреждения ДОЛЖНА добавляться подсказка о питании платы и выводе VREF/3V3. `[R]`

### 3.6. Чтение памяти

3.6.1. Чтение слова (READDEBUGREG) и блока (READMEM_32BIT) ДОЛЖНО принимать только адрес,
выровненный на 4, в диапазоне `0…0xFFFFFFFF`; иначе — ошибка `BAD_ARGUMENT` без обмена с адаптером.
`[R]`

3.6.2. Одна команда READMEM_32BIT ДОЛЖНА читать не более `MAX_BLOCK_BYTES = 1024` байт, кратно 4, и
НЕ ДОЛЖНА пересекать границу 1 КБ адресного пространства. Причина: автоинкремент TAR гарантирован
только в пределах 1 КБ. `[R]`

3.6.3. Запрос блока произвольной длины ДОЛЖЕН разбиваться на команды по п. 3.6.2 с разрезом на
границах 1 КБ. `[R]`

3.6.4. После каждой команды READMEM_32BIT ДОЛЖНО запрашиваться состояние (п. 3.4.6); при WAIT блок
ДОЛЖЕН читаться заново по п. 3.3.2, при другом отказе — ошибка `SWD_FAULT` с адресом и длиной блока.
`[R]`

3.6.5. Данные блока, для которого состояние не равно `STATUS_OK`, НЕ ДОЛЖНЫ передаваться
потребителю. `[R]`

## 4. Опознание цели

### 4.1. Порядок

4.1.1. Опознание ДОЛЖНО выполняться только чтением, в порядке: (а) CPUID по адресу `0xE000ED00`; (б)
регистр BASE MEM-AP 0 (если доступен по п. 3.4.7); (в) идентификаторы ROM-таблицы (PIDR, CIDR); (г)
регистр идентификатора семейства по списку кандидатов для ядра; (д) размер Flash. `[R]`

4.1.2. Отказ `SWD_FAULT` или `BAD_ARGUMENT` на любом шаге ДОЛЖЕН записываться в примечания
результата и НЕ ДОЛЖЕН прерывать опознание. Ошибки транспорта (`USB_IO`, `PROTOCOL`) ДОЛЖНЫ
прерывать опознание. `[R]`

### 4.2. ROM-таблица

4.2.1. Адрес ROM-таблицы ДОЛЖЕН браться из BASE MEM-AP (`base & 0xFFFFF000`); значение `0xFFFFFFFF`
ДОЛЖНО означать «нет компонентов». Если BASE не прочитан, ДОЛЖЕН использоваться адрес по умолчанию
`ROM_DEFAULT_BASE = 0xE00FF000`, а источник адреса — указываться в результате. `[R]`

4.2.2. Производитель ДОЛЖЕН определяться по коду JEP106 из PIDR ROM-таблицы; CIDR, не
соответствующий CoreSight, ДОЛЖЕН отмечаться в примечаниях. `[R]`

### 4.3. Семейство и серия

4.3.1. Кандидаты регистра идентификатора ДОЛЖНЫ выбираться по ядру: `0xE0042000` (Cortex-M3/M4/M7
STM32, AT32), `0x40015800` (Cortex-M0/M0+ STM32), `0x5C001000` (STM32H7). Значения `0` и
`0xFFFFFFFF` ДОЛЖНЫ считаться непрочитанными. `[R]`

4.3.2. Если значение похоже на DBGMCU_IDCODE STM32, серия ДОЛЖНА определяться по DEV_ID по
справочнику модуля. Если при этом ROM-таблица корректна и производитель не ST, цель ДОЛЖНА
отмечаться как «STM32-совместимый» с примечанием о возможных GD32, APM32, CKS32. `[R]`

4.3.3. AT32 ДОЛЖЕН опознаваться эвристикой по формату PID в `0xE0042000` с примечанием «эвристика».
`[R]`

4.3.4. Номер part ROM-таблицы НЕ ДОЛЖЕН использоваться для определения серии STM32. Причина: у
STM32F411 part равен `0x411` при DEV_ID `0x431`. `[U]`

4.3.5. Размер Flash ДОЛЖЕН читаться 16-битным словом по адресу F_SIZE из справочника серии (для AT32
— `0x1FFFF7E0`). `[R]`

### 4.4. Результат

4.4.1. Результат опознания ДОЛЖЕН содержать: CPUID и имя ядра с ревизией, адрес и источник адреса
ROM-таблицы, производителя по JEP106, адрес и значение регистра идентификатора, семейство, серию
STM32 (если найдена), размер Flash и SRAM (если известны), примечания. `[R]`

4.4.2. Результат НЕ ДОЛЖЕН содержать уникальный идентификатор (UID) микроконтроллера; модуль НЕ
ДОЛЖЕН читать область UID. `[R]`

## 5. Функциональные требования: жизненный цикл и API

### 5.1. Поиск адаптеров

5.1.1. Поиск ДОЛЖЕН возвращать все подключённые устройства с VID `0x0483` и PID из таблицы
приложения A, упорядоченные по `deviceName`. `[R]`

5.1.2. При отсутствии у телефона функции USB Host открытие адаптера ДОЛЖНО завершаться ошибкой
«Телефон не поддерживает USB Host (OTG)». `[R]`

5.1.3. Поиск НЕ ДОЛЖЕН читать серийный номер устройства USB. `[R]`

### 5.2. Разрешение USB

5.2.1. Если разрешения нет, ДОЛЖЕН показываться системный запрос; результат ДОЛЖЕН возвращаться в
главный поток. `[R]`

5.2.2. `PendingIntent` запроса ДОЛЖЕН быть явным (с пакетом приложения) и изменяемым на Android 12+;
приёмник ответа ДОЛЖЕН регистрироваться как неэкспортируемый на Android 13+. `[R]`

5.2.3. Ответ на запрос разрешения ДОЛЖЕН сопоставляться с устройством по `UsbManager.EXTRA_DEVICE`;
ответ для другого устройства НЕ ДОЛЖЕН завершать ожидание. Причина: при нескольких адаптерах запросы
идут подряд. `[U]`

5.2.4. Подключение адаптера, для которого приложение открыто фильтром `USB_DEVICE_ATTACHED`, ДОЛЖНО
обходиться без повторного запроса разрешения. `[R]`

### 5.3. Открытие

5.3.1. Открытие ДОЛЖНО: (а) проверить разрешение; (б) найти интерфейс отладки по п. 3.1.2; (в)
открыть устройство; (г) захватить интерфейс с отключением драйвера ядра. Отказ на каждом шаге ДОЛЖЕН
сообщаться своим видом причины: нет USB Host, нет разрешения, нет интерфейса, не открылось, не
захватилось. `[R]`

5.3.2. Транспорт ST-Link ДОЛЖЕН захватывать только интерфейс отладки. Закрытие транспорта ДОЛЖНО
освобождать только этот интерфейс и только своё соединение `UsbDeviceConnection`. Другие интерфейсы
того же устройства (VCP у ST-Link V2-1 и V3) обслуживает модуль USB-UART через собственное
соединение или через общее соединение реестра USB; способ выбирается по проверке на оборудовании
(TC-25). `[N]` (р.1.1)

### 5.4. Подключение (`connect`)

5.4.1. Подключение ДОЛЖНО выполнять шаги строго в порядке: (а) версия (п. 3.4); (б) проверка
минимальной прошивки (п. 3.4.5); (в) текущий режим; (г) выход из DFU, SWIM или отладки, если адаптер
в одном из них; (д) напряжение цели (п. 3.5); (е) вход в SWD; (ж) DP IDCODE. `[R]`

5.4.2. DP IDCODE, равный `0` или `0xFFFFFFFF`, ДОЛЖЕН сообщаться ошибкой `NO_TARGET`. `[R]`

5.4.3. Результат подключения ДОЛЖЕН содержать версию, исходный режим адаптера, напряжение (или «не
измеряется»), DP IDCODE и список предупреждений (старая прошивка без READ_DAP_REG, низкое
напряжение). `[R]`

5.4.4. Подключение НЕ ДОЛЖНО останавливать и сбрасывать ядро цели. `[R]`

### 5.5. Чтение (`read32`, `readBlock`, `readApRegister`)

5.5.1. `read32(address)` ДОЛЖЕН возвращать слово по п. 3.6.1 и 3.3.2. `[R]`

5.5.2. `readBlock(address, words)` ДОЛЖЕН возвращать `words` слов по п. 3.6.2–3.6.5. `[R]`

5.5.3. `readApRegister(ap, register)` ДОЛЖЕН возвращать значение регистра или «нет значения» по
п. 3.4.7. `[R]`

5.5.4. Операции чтения ДОЛЖНЫ быть доступны потребителям через интерфейс `DebugMemory` (раздел 6.2),
не раскрывающий команды адаптера. `[R]`

### 5.6. Отключение (`disconnect`)

5.6.1. Отключение ДОЛЖНО отправить DEBUG_EXIT, если сеанс вошёл в SWD, и игнорировать ошибки этой
команды. Ядро цели продолжает работу. `[R]`

5.6.2. Повторное отключение и отключение после физического удаления адаптера ДОЛЖНЫ завершаться без
исключений. `[U]`

### 5.7. Ошибки

5.7.1. Все ошибки модуля ДОЛЖНЫ передаваться исключением `StLinkException` с видом: `USB_IO`,
`PROTOCOL`, `NO_TARGET`, `SWD_FAULT`, `OLD_FIRMWARE`, `UNSUPPORTED_ADAPTER`, `BAD_ARGUMENT`; при
отказе адаптера — с кодом состояния. `[R]`

5.7.2. Текст ошибки ДОЛЖЕН быть на русском и содержать действие для пользователя, если оно известно.
`[R]`

### 5.8. Журнал обмена

5.8.1. Каждая команда ДОЛЖНА записываться строкой вида `> f1 80` (байты без завершающих нулей),
каждый ответ — строкой вида `< 29 47 83 04 48 37`. `[R]`

5.8.2. Ответ длиннее `LOG_MAX_BYTES = 16` байт ДОЛЖЕН записываться комментарием `# < N байт: …` с
первыми 16 байтами. Причина: блоки памяти не нужны для тестов воспроизведения и раздувают журнал.
`[R]`

5.8.3. Формат журнала ДОЛЖЕН совпадать с форматом записей `stlink/src/test/resources/captures/`,
чтобы журнал с телефона можно было без правки превратить в тест воспроизведения. `[R]`

5.8.4. Журнал НЕ ДОЛЖЕН содержать серийный номер адаптера и UID цели. `[R]`

### 5.9. Несколько адаптеров

5.9.1. Модуль ДОЛЖЕН допускать одновременную работу нескольких сеансов `StLink`, каждый со своим
транспортом; протокольная часть НЕ ДОЛЖНА хранить состояние вне объекта сеанса. `[N]`

5.9.2. Каждый сеанс ДОЛЖЕН использоваться из одного потока исполнения; модуль НЕ ДОЛЖЕН требовать
синхронизации между сеансами. `[N]`

5.9.3. Ошибка, таймаут или отключение одного адаптера НЕ ДОЛЖНЫ влиять на обмен с другими. `[N]`

5.9.4. Строки журнала обмена ДОЛЖНЫ различаться по адаптеру, если открыто больше одного сеанса
(префикс имени прибора, например `stlink1`). `[N]`

### 5.10. Повторное подключение (р.1.1)

5.10.1. После физического переподключения адаптера модуль ДОЛЖЕН выполнять подключение заново
полностью по п. 5.2–5.4: прежние транспорт и сеанс недействительны. Причина: Android выдаёт
переподключённому устройству новый `deviceName` и, как правило, требует нового разрешения. `[N]`
(р.1.1)

5.10.2. Модуль ДОЛЖЕН вычислять отпечаток связки «адаптер — цель»: модель адаптера (VID:PID), метка
версии прошивки (п. 3.4.3), DP IDCODE, CPUID, адрес и значение регистра идентификатора семейства,
размер Flash и для STM32 и AT32 — два первых слова Flash по адресу `FLASH_BASE = 0x08000000`
(начальный указатель стека и вектор сброса). Отпечаток НЕ ДОЛЖЕН содержать серийный номер адаптера
и UID цели. `[N]` (р.1.1)

5.10.3. Если отпечаток нового подключения совпадает с отпечатком сеанса, потерянного при отключении,
модуль ДОЛЖЕН считать его тем же прибором: восстановить метку прибора, список полей, опрос и запись,
а в события и запись MCAP добавить событие «переподключение» с длительностью разрыва. `[N]` (р.1.1)

5.10.4. Если совпадает адаптер, но отличается часть отпечатка, относящаяся к цели, модуль ДОЛЖЕН
сообщить «другая плата или другая прошивка» с перечнем отличий и НЕ ДОЛЖЕН возобновлять опрос полей
прежнего сеанса без подтверждения пользователя. Причина: адреса полей из `addresses.json` привязаны
к прошивке. `[N]` (р.1.1)

5.10.5. Если отпечаток совпадает с несколькими потерянными сеансами (два одинаковых адаптера с
одинаковыми платами и прошивкой), модуль ДОЛЖЕН предложить пользователю выбрать сеанс. Такие связки
функционально равноценны и различаются только метками. `[N]` (р.1.1)

5.10.6. Ожидание переподключения СЛЕДУЕТ ограничивать `RECONNECT_WAIT_S = 60` с; после этого
потерянный сеанс закрывается, а его запись MCAP завершается. `[N]` (р.1.1)

### 5.11. Управление ядром и разрешение на изменение цели (р.2.0)

5.11.1. Интерфейс `TargetWrite` ДОЛЖЕН выдаваться только при предъявлении объекта разрешения,
который приложение создаёт после включения пользователем режима «Изменение цели» в режиме эксперта.
Без разрешения модуль ведёт себя как в ревизиях 1.x. `[N]` (р.2.0)

5.11.2. Остановка (`halt`) ДОЛЖНА записывать в DHCSR `0xA05F0003` (C_DEBUGEN | C_HALT) и ждать
S_HALT не дольше `HALT_TIMEOUT_MS = 500` мс. `[N]` (р.2.0)

5.11.3. Запуск (`go`) ДОЛЖЕН записывать в DHCSR `0xA05F0001` (C_DEBUGEN без C_HALT) и проверять, что
S_HALT снят. `[N]` (р.2.0)

5.11.4. Сброс с запуском (`reset`) ДОЛЖЕН записывать в AIRCR `0x05FA0004` (SYSRESETREQ); после
сброса модуль ДОЛЖЕН заново читать DP IDCODE, потому что сброс может разорвать сеанс SWD. `[N]`
(р.2.0)

5.11.5. Сброс с остановкой (`resetHalt`) ДОЛЖЕН: (а) установить в DEMCR бит VC_CORERESET
с сохранением прочих битов; (б) выполнить сброс по п. 5.11.4; (в) дождаться S_HALT; (г) вернуть
DEMCR в прежнее значение. `[N]` (р.2.0)

5.11.6. Если сброс по AIRCR не останавливает ядро за `HALT_TIMEOUT_MS`, модуль ДОЛЖЕН сообщить
об этом и МОЖЕТ предложить аппаратный сброс выводом NRST (DRIVE_NRST, импульс) только если вывод
NRST адаптера подключён — это подтверждает пользователь. `[N]` (р.2.0)

5.11.7. Состояние ядра ДОЛЖНО показываться по DHCSR: работает, остановлено, sleep, lockup,
был сброс (S_RESET_ST). `[N]` (р.2.0)

5.11.8. При отключении (`disconnect`) после остановки модуль ДОЛЖЕН спросить, запустить ли ядро;
по умолчанию — запустить (DHCSR `0xA05F0001`), затем снять C_DEBUGEN (DHCSR `0xA05F0000`). `[N]`
(р.2.0)

5.11.9. Каждая команда изменения цели ДОЛЖНА записываться в журнал обмена так же, как команды
чтения,
и в историю операций с временем, адресом и результатом. `[N]` (р.2.0)

## 6. Требования к интерфейсам

### 6.1. Транспорт

6.1.1. Протокольная часть ДОЛЖНА обращаться к USB только через интерфейс `StLinkTransport` с
операциями `write(bytes)`, `read(length)`, `close()`. `[R]`

6.1.2. Реализация транспорта поверх `UsbManager` ДОЛЖНА находиться в модуле `usb`; модуль `stlink`
НЕ ДОЛЖЕН зависеть от Android. `[R]`

6.1.3. Для тестов ДОЛЖЕН существовать транспорт воспроизведения, который проверяет каждую команду по
журналу и выдаёт записанный ответ. `[R]`

### 6.2. Потребители

6.2.1. Интерфейс `DebugMemory` ДОЛЖЕН предоставлять операции `read32`, `read16` (через `read32`),
`readBlock`, `readApRegister`. `[R]`

6.2.2. Через `DebugMemory` НЕ ДОЛЖНО быть доступно ни одной операции записи; запись выполняется
только через `TargetWrite` (п. 6.2.3). `[N]` (р.2.0)

6.2.3. Интерфейс `TargetWrite` ДОЛЖЕН предоставлять: `write32(адрес, значение)`, `writeBlock32`,
`writeBlock16`, `writeBytes`, `halt`, `go`, `reset`, `resetHalt`, `pulseNrst`, `coreState`. `[N]`
(р.2.0)

### 6.3. Реестр приборов

6.3.1. Модуль ДОЛЖЕН сообщать реестру приборов модель адаптера, `deviceName`, версию прошивки и

## 7. Нефункциональные требования

### 7.1. Быстродействие

7.1.1. Чтение одного слова (`read32`) без WAIT СЛЕДУЕТ выполнять не дольше 5 мс на ST-Link/V2 при
прямом подключении к телефону; подтверждается замером по журналу с метками времени. `[N]`

7.1.2. Чтение блока 1 КБ без WAIT СЛЕДУЕТ выполнять не дольше 20 мс; резервная копия 512 КБ Flash —
не дольше 15 с. `[N]`

7.1.3. Модуль ДОЛЖЕН обеспечивать опрос полей с периодом 100 мс (10 Гц) на одном адаптере без
пропуска циклов, если поля укладываются в 2 блока чтения. `[R]`

### 7.2. Надёжность

7.2.1. Физическое отключение адаптера во время обмена ДОЛЖНО завершать текущую операцию ошибкой
`USB_IO` не позднее чем через `USB_TIMEOUT_MS`, без зависания потока. `[R]`

7.2.2. После ошибки `USB_IO` сеанс ДОЛЖЕН считаться закрытым; повторное подключение — новым сеансом.
`[U]`

### 7.3. Безопасность цели

7.3.1. Без разрешения на изменение цели (п. 5.11.1) побочные эффекты ДОЛЖНЫ ограничиваться сбросом
липких битов S_RETIRE_ST и S_RESET_ST при чтении DHCSR. `[R]` (р.2.0)

7.3.2. Модуль НЕ ДОЛЖЕН читать регистры периферии с побочным эффектом чтения «заодно» в составе
блока; решение о составе блоков принимает потребитель (`telemetry`, `ReadPlan`). `[R]`

### 7.4. Приватность

7.4.1. Модуль НЕ ДОЛЖЕН читать, хранить и передавать серийный номер адаптера (строковый дескриптор
`iSerialNumber`) и UID цели. `[R]`

### 7.5. Переносимость

7.5.1. Модуль `stlink` ДОЛЖЕН собираться и тестироваться на JVM 17 без Android SDK. `[R]`

### 7.6. Сопровождаемость

7.6.1. Каждое требование ДОЛЖНО быть прослеживаемо до кода и проверки (раздел 9). `[N]`

7.6.2. Каждая новая поддержанная плата или адаптер СЛЕДУЕТ сопровождать записью обмена в `captures/`
и тестом воспроизведения, проверенной на отсутствие серийных номеров и UID. `[R]`

## 10. Допущения и открытые вопросы

### 10.1. Допущения

10.1.1. Цель — Cortex-M с MEM-AP 0, отображающим системную шину (ADIv5). Затрагивает разделы 3–4.

10.1.2. DEBUG_EXIT не останавливает и не сбрасывает ядро на всех поддерживаемых прошивках адаптера;
подтверждено журналами шести плат с адаптерами V2 и V2-1. Затрагивает п. 3.2.3, 5.6.1.

10.1.3. ST-Link V3 поддерживается по документации и синтетическому журналу; на оборудовании не
проверялся. Затрагивает п. 3.4.2.

10.1.4. Android допускает два соединения `UsbDeviceConnection` к одному устройству с захватом разных
интерфейсов (отладка и VCP). Затрагивает п. 5.3.2; проверяется TC-25. (р.1.1)

### 10.2. Вопросы и решения

| № | Вопрос | Статус | Решение / комментарий | Пункты |
| :---: | :--- | :---: | :--- | :--- |

Переподключение — новое подключение; тот же прибор узнаётся по отпечатку связки «адаптер — цель», при неоднозначности выбирает пользователь. | 5.10.1–5.10.6 |

10.3.1. Поддержка CMSIS-DAP (DAPLink, Picoprobe, WCH-Link) удобна через тот же интерфейс

ITM; можно предложить как функцию для прошивок, которые это делают.

## Приложение B. Соглашение о ссылках на ТЗ из кода

B.1. Ссылка на требование оформляется однострочным комментарием рядом с реализацией:
`// ТЗ ST-Link 3.6.2`. Для нескольких требований — перечисление через запятую:
`// ТЗ ST-Link 3.3.2, 3.3.3`. Имя ТЗ в ссылке обязательно: в проекте несколько ТЗ.

B.2. Для тестов используется идентификатор тест-кейса и номера проверяемых требований, например:
`// TC-10: ТЗ ST-Link 3.6.2–3.6.5`.

B.3. Пример:

```kotlin
// ТЗ ST-Link 3.6.2: автоинкремент TAR гарантирован только в пределах 1 КБ.
require((address and 0x3FFL) + length <= 0x400L) { "Блок пересекает границу 1 КБ" }
```

B.4. При удалении требования из документа его номер сохраняется с пометкой «(исключено)» (п. 1.6.2);
комментарий в коде удаляется вместе с реализацией.
