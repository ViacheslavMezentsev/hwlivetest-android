## 1. Введение

### 1.1. Назначение документа

1.1.1. Документ определяет требования к модулю поддержки последовательных портов USB: виртуальных
COM-портов класса CDC-ACM (VCP ST-Link V2-1 и V3, прошивки STM32 с USB CDC, BlackPill) и мостов
USB-UART распространённых производителей. Модуль принимает данные с метками времени, показывает их,
разбирает числа в потоки для графиков и пишет в MCAP.

1.1.2. Документ является основой для реализации и верификации кода: каждое требование имеет
уникальный номер, на который ссылаются комментарии в коде, тесты и матрица прослеживаемости (раздел
9).

### 1.2. Область применения

1.2.1. Требования применимы к модулю `serial` (протоколы мостов, кадрирование, разбор,
представление) и к части модуля `usb`, обслуживающей порты (асинхронный транспорт).

1.2.2. Документ не описывает экран терминала, декодирование UART по отсчётам логического анализатора
(ТЗ `decoders`) и протоколы поверх UART (SLCAN, Modbus, MAVLink) — для них определён только контракт
доступа к потоку байтов (п. 6.2).

### 1.3. Метод формирования

1.3.1. Требования сформированы с нуля. Источники: спецификация USB CDC 1.2 и PSTN 1.2, документация
Silicon Labs AN571 (CP210x), FTDI AN232B-04 и AN_120 (FT232R, FT2232, FT232H), Prolific (PL2303),
WCH (CH340/CH341). Драйверы CDC-ACM и мостов берутся готовыми из библиотеки usb-serial-for-android
(лицензия MIT, версия 3.9.0); код драйверов ядра Linux (GPL) не используется. (р.1.1)

1.3.2. Кода модуля нет, поэтому все требования имеют маркер `[N]`.

1.3.3. В случае расхождения между этим документом и кодом расхождение считается дефектом одного из
них и разрешается пересмотром ревизии документа.

### 1.4. Термины и сокращения

| Термин | Определение |
| :--- | :--- |
| Порт | Один последовательный канал: интерфейс CDC-ACM или канал моста. |
| CDC-ACM | Класс USB «Communications Device, Abstract Control Model»: виртуальный COM-порт. |
| VCP | Virtual COM Port — порт CDC-ACM, встроенный в отладчик или прошивку. |
| Мост | Микросхема USB-UART со своим протоколом управления (CH340, CP2102, FT232R, PL2303). |
| Параметры линии | Скорость, число битов данных, чётность, число стоп-битов. |
| Линии управления | DTR и RTS (выходы), CTS, DSR, DCD, RI (входы). |
| Блок | Данные одной завершённой передачи USB с меткой времени. |
| Строка | Байты между разделителями строк после кадрирования (п. 4.2). |
| Профиль порта | Сохранённые параметры линии, состояние DTR/RTS, кодировка и правила разбора для порта. |

## 2. Общее описание

### 2.1. Контекст

2.1.1. Прошивки обычно печатают в UART журнал и значения. Пользователь подключает к телефону мост
USB-UART (к выводам TX/RX/GND платы), отладчик с VCP (ST-Link V2-1 на Nucleo уже соединён с USART2
платы) или саму плату с USB CDC. Модуль принимает данные, показывает их рядом с полями, прочитанными
через ST-Link, и пишет в ту же запись MCAP.

### 2.2. Функции модуля

2.2.1. Поиск портов: CDC-ACM по классу интерфейса, мосты — по VID:PID.

2.2.2. Настройка параметров линии и линий управления.

2.2.3. Приём с метками времени; кадрирование строк; текст и HEX.

2.2.4. Разбор чисел из строк в скалярные потоки для графиков.

2.2.5. Запись принятых данных, строк и чисел в MCAP.

2.2.6. Передача данных в порт — только после явного согласия пользователя.

### 2.3. Роли и потребители

| Роль | Взаимодействие |
| :--- | :--- |
| Экраны (`app`) | Список портов, параметры, терминал, включение передачи. |
| Графики (`telemetry`) | Скалярные потоки из разобранных строк. |
| Протоколы поверх UART | Поток байтов с метками времени (п. 6.2). |
| Запись (`recorder`) | Каналы байтов, строк, чисел. |
| Сессии и агент | Карточка фрагмента терминала, поиск в принятом тексте. |

### 2.4. Границы

2.4.1. Вне области ТЗ: RS-485 с управлением направлением, аппаратное управление потоком RTS/CTS как
функция приёма (линии только читаются), Bluetooth SPP, порты, обслуживаемые драйверами ядра,
программирование микроконтроллеров через загрузчик UART.

### 2.5. Ограничения платформы

2.5.1. Кадрирование, разбор и профиль порта (`serial`) — Kotlin/JVM без зависимостей от Android.
Драйверы портов — библиотека usb-serial-for-android в модуле `usb` за интерфейсом порта. (р.1.1)

2.5.2. Доступ к USB — только Android USB Host API, без root.

## 3. Драйверы портов

### 3.1. Общие требования

3.1.1. Каждый драйвер ДОЛЖЕН реализовывать операции: открыть порт, задать параметры линии, задать
DTR и RTS, прочитать состояние входных линий (если мост это умеет), запустить приём, передать байты,
закрыть. `[N]`

3.1.2. Драйвер ДОЛЖЕН отвергать неподдерживаемые мостом параметры линии ошибкой `BAD_CONFIG` до
обращения к прибору и сообщать ближайшую поддерживаемую скорость. `[N]`

3.1.3. Скорость ДОЛЖНА задаваться в диапазоне `300…12 000 000` бит/с с учётом предела моста
(приложение C); биты данных — 5–8; чётность — нет, нечёт, чёт, маркер, пробел; стоп-биты — 1, 1,5, 2.
`[N]`

3.1.4. Многоканальные мосты (FT2232, FT4232, CP2105, CP2108) и устройства с несколькими VCP (ST-Link
V3) ДОЛЖНЫ давать отдельный порт на каждый канал. `[N]`

3.1.5. Драйвер CDC-ACM ДОЛЖЕН быть собственным (модуль `usb`, без сторонних библиотек). Драйверы
мостов CH34x, CP210x, FTDI, PL2303 ДОЛЖНЫ браться из библиотеки usb-serial-for-android закреплённой
версии (`3.9.0`), когда до них дойдёт дело. И те и другие используются только через интерфейс порта
модуля, чтобы замена драйвера не затрагивала остальной код. `[N]` (р.1.3)

### 3.2. CDC-ACM

3.2.1. Портом CDC-ACM ДОЛЖНА считаться пара интерфейсов: управляющий (класс `0x02`, подкласс `0x02`)
и данных (класс `0x0A`) с bulk IN и bulk OUT; пара определяется по дескриптору Union, при его
отсутствии — по соседству интерфейсов. `[N]`

3.2.2. Порт CDC-ACM ДОЛЖЕН находиться и на составных устройствах, в том числе у ST-Link V2-1 и V3,
без опоры на VID:PID. `[N]`

3.2.3. Параметры линии ДОЛЖНЫ задаваться запросом `SET_LINE_CODING` (`0x20`, тип `0x21`, 7 байт:
скорость `uint32` LE, стоп-биты, чётность, биты данных); DTR и RTS — запросом
`SET_CONTROL_LINE_STATE` (`0x22`, бит 0 — DTR, бит 1 — RTS). `[N]`

3.2.4. Если устройство не поддерживает `SET_LINE_CODING` (отвечает STALL), порт ДОЛЖЕН открываться
без задания параметров с предупреждением в журнале. Причина: многие прошивки с USB CDC скорость
игнорируют. `[N]`

3.2.5. Уведомления `SERIAL_STATE` с точки прерываний СЛЕДУЕТ принимать и превращать в события:
ошибки кадра и чётности, BREAK, переполнение, изменение DCD и DSR. `[N]`

### 3.3. Мосты

3.3.1. Модуль ДОЛЖЕН поддерживать мосты: WCH CH340/CH341, Silicon Labs CP210x, FTDI
FT232R/FT-X/FT2232/FT4232/FT232H, Prolific PL2303 — по таблице VID:PID приложения C. `[N]`

3.3.2. Таблица VID:PID мостов ДОЛЖНА быть расширяемой данными без изменения логики. `[N]`

3.3.3. Драйвер FTDI ДОЛЖЕН удалять два байта состояния в начале каждого пакета USB и превращать их в
события ошибок линии. `[N]`

3.3.4. Драйвер FTDI ДОЛЖЕН задавать таймер задержки `FTDI_LATENCY_MS = 1` мс. Причина: при значении
по умолчанию 16 мс метки времени строк становятся грубыми. `[N]`

3.3.5. Для мостов, которые не сообщают ошибки линии, модуль ДОЛЖЕН показывать «ошибки линии не
отслеживаются». `[N]`

3.3.6. Мосты СЛЕДУЕТ проверять на оборудовании в порядке: CDC-ACM (свой анализатор на BlackPill, VCP
ST-Link V2-1), CH340, CP210x, FTDI, PL2303 (по распространённости у плат с STM32). `[N]` (р.1.3)

### 3.4. Линии управления и безопасность цели

3.4.1. Модуль НЕ ДОЛЖЕН менять DTR и RTS без действия пользователя, кроме установки состояния из
профиля порта при открытии. Причина: на многих платах DTR и RTS подключены к сбросу и BOOT (Arduino,
ESP32, схемы автозагрузки STM32), и их переключение перезапускает цель. `[N]`

3.4.2. Профиль по умолчанию ДОЛЖЕН быть: для CDC-ACM — DTR = 1, RTS = 0 (прошивки с USB CDC часто
ждут DTR, прежде чем передавать); для мостов — DTR = 0, RTS = 0 (линии неактивны, как сразу после
подключения). `[N]`

3.4.3. Изменение DTR или RTS пользователем ДОЛЖНО сопровождаться предупреждением «может
перезапустить плату» один раз за сессию для порта. `[N]`

3.4.4. При выборе скорости 1200 бит/с на порту CDC-ACM модуль ДОЛЖЕН предупреждать: открытие и
закрытие порта на 1200 бит/с переводит Arduino и RP2040 в загрузчик. `[N]`

## 4. Поток данных и представление

### 4.1. Приём

4.1.1. Приём ДОЛЖЕН выполняться асинхронно: в очереди постоянно стоят не менее `RX_QUEUE = 4`
запросов по `RX_BUF_BYTES = 16384` байт. `[N]`

4.1.2. Каждый блок ДОЛЖЕН получать метку времени в общей шкале платформы (`elapsedRealtimeNanos`) в
момент завершения передачи USB. `[N]`

4.1.3. Принятые байты ДОЛЖНЫ храниться без изменений; кадрирование, кодировка и разбор применяются
только к представлению. `[N]`

4.1.4. Модуль ДОЛЖЕН хранить в памяти не менее `RX_HISTORY_BYTES = 8 МБ` последних принятых данных
на порт кольцевым буфером; вытеснение старых данных ДОЛЖНО отмечаться в представлении. `[N]`

### 4.2. Кадрирование строк

4.2.1. Разделитель строк ДОЛЖЕН выбираться: `\n`, `\r\n`, `\r` или «авто» (любой из них; `\r\n`
считается одним разделителем). `[N]`

4.2.2. Строка длиннее `MAX_LINE_BYTES = 4096` байт ДОЛЖНА разрываться принудительно с пометкой.
`[N]`

4.2.3. Метка времени строки ДОЛЖНА быть меткой блока, в котором пришёл её первый байт. `[N]`

4.2.4. Неполная последняя строка ДОЛЖНА показываться сразу, не дожидаясь разделителя, и дополняться
по мере прихода данных. `[N]`

### 4.3. Представление

4.3.1. Текст ДОЛЖЕН показываться в кодировке профиля: UTF-8 (по умолчанию), ASCII или Windows-1251;
непечатаемые и неверные байты — заменой с кодом (`\x1B`). `[N]`

4.3.2. Управляющие последовательности ANSI цвета (`ESC [ … m`) СЛЕДУЕТ применять как цвет текста,
прочие — показывать заменой. `[N]`

4.3.3. Режим HEX ДОЛЖЕН показывать байты по 16 в строке со смещением и меткой времени блока. `[N]`

4.3.4. Каждая строка МОЖЕТ показываться с меткой времени: абсолютной (часы телефона до миллисекунд)
или относительной от начала приёма. `[N]`

### 4.4. Разбор чисел

4.4.1. Модуль ДОЛЖЕН выделять из строк пары «имя — число» по умолчанию в формах `имя=число` и
`имя: число`, где число — десятичное с точкой, знаком и экспонентой. `[N]`

4.4.2. Пользователь ДОЛЖЕН иметь возможность задать правило разбора регулярным выражением с
именованными группами или как CSV с заголовком. `[N]`

4.4.3. Каждое имя ДОЛЖНО становиться скалярным потоком `/<порт>/<имя>` с меткой времени строки;
поток доступен графикам вместе с полями ST-Link. `[N]`

4.4.4. Строки, в которых не найдено чисел, НЕ ДОЛЖНЫ создавать потоков; ошибки разбора НЕ ДОЛЖНЫ
прерывать приём. `[N]`

### 4.5. Передача

4.5.1. Передача в порт ДОЛЖНА быть выключена по умолчанию; включение требует явного подтверждения
пользователя для порта на время сессии. Причина: передача — воздействие на цель (п. 1 «Принципы»
архитектуры). `[N]`

4.5.2. Агент НЕ ДОЛЖЕН передавать данные в порт без подтверждения пользователя на каждую передачу.
`[N]`

4.5.3. Переданные байты ДОЛЖНЫ записываться в журнал порта и в MCAP (`/<порт>/tx`) с меткой времени.
`[N]`

4.5.4. Окончание строки при передаче ДОЛЖНО выбираться: нет, `\n`, `\r`, `\r\n`. `[N]`

## 5. Функциональные требования: жизненный цикл и API

### 5.1. Поиск

5.1.1. Поиск ДОЛЖЕН возвращать все порты всех подключённых устройств: CDC-ACM (п. 3.2.1) и мосты
(п. 3.3.1) с именем устройства, номером канала и названием («ST-Link/V2-1 VCP», «CP2102N»). `[N]`

5.1.2. Поиск НЕ ДОЛЖЕН читать серийный номер устройства. `[N]`

5.1.3. Порт ДОЛЖЕН находиться и на устройстве, уже открытом другим прибором платформы (п. 6.1.2).
`[N]`

### 5.2. Открытие (`open`)

5.2.1. Открытие ДОЛЖНО: (а) проверить разрешение; (б) захватить интерфейсы порта; (в) выполнить
инициализацию моста; (г) задать параметры линии и линии управления по профилю (п. 3.4.2); (д)
запустить приём. `[N]`

5.2.2. Профиль порта ДОЛЖЕН запоминаться по модели устройства и номеру канала и применяться при
следующем открытии. `[N]`

5.2.3. Изменение параметров линии на открытом порту ДОЛЖНО применяться без закрытия порта и без
потери данных в буфере. `[N]`

### 5.3. Закрытие (`close`)

5.3.1. Закрытие ДОЛЖНО остановить приём, отменить запросы, освободить интерфейсы порта и НЕ ДОЛЖНО
менять DTR и RTS. Повторное закрытие и закрытие после отключения — без исключений. `[N]`

5.3.2. Закрытие порта на составном устройстве НЕ ДОЛЖНО закрывать соединение USB, если им пользуется
другой прибор (п. 6.1.2). `[N]`

### 5.4. Отключение устройства

5.4.1. Отключение устройства во время приёма ДОЛЖНО завершать приём с событием «порт отключён» не
позднее чем через 1 с; принятые данные ДОЛЖНЫ сохраняться. `[N]`

5.4.2. При повторном подключении того же устройства (та же модель и канал) СЛЕДУЕТ предлагать
возобновить приём с прежним профилем. `[N]`

### 5.5. Ошибки

5.5.1. Ошибки ДОЛЖНЫ передаваться исключением с видом: `USB_IO`, `NO_PERMISSION`, `CLAIM_FAILED`,
`BAD_CONFIG`, `UNSUPPORTED_BRIDGE`, `TX_DISABLED`; текст — на русском с действием для пользователя.
`[N]`

### 5.6. Журнал

5.6.1. Управляющие запросы драйвера (параметры линии, DTR/RTS, инициализация моста) ДОЛЖНЫ
записываться в журнал обмена тем же форматом, что у ST-Link; принимаемые данные — сводкой (байт,
скорость). `[N]`

5.6.2. Журнал НЕ ДОЛЖЕН содержать серийный номер устройства. `[N]`

## 6. Требования к интерфейсам

### 6.1. Транспорт и USB

6.1.1. Протокольная часть ДОЛЖНА обращаться к USB только через интерфейс транспорта: управляющий
запрос OUT и IN, асинхронный приём, передача bulk OUT, закрытие. `[N]`

6.1.2. Порт ДОЛЖЕН открываться собственным соединением `UsbDeviceConnection` и захватывать только
интерфейсы своего порта; закрытие порта закрывает только это соединение. Причина: библиотека
закрывает соединение при закрытии порта, а VCP ST-Link V2-1 должен работать одновременно с отладкой
(ТЗ ST-Link, п. 5.3.2, допущение 10.1.4). `[N]` (р.1.1)

6.1.3. Для тестов ДОЛЖЕН существовать транспорт-имитатор, записывающий управляющие запросы и
выдающий заданные блоки данных. `[N]`

### 6.2. Потребители потока

6.2.1. Модуль ДОЛЖЕН предоставлять подписку на поток блоков (метка времени, байты) и на поток строк
(метка времени, текст, байты); подписчики получают данные в своём потоке исполнения и не задерживают
приём. `[N]`

### 6.3. Запись

6.3.1. Запись в MCAP ДОЛЖНА создавать каналы: `/<порт>/rx` и `/<порт>/tx` со схемой ROS 1
`hwlivetest_msgs/SerialChunk` (`uint8[] data`), `/<порт>/lines` со схемой `std_msgs/String`,
`/<порт>/<имя>` со схемой `std_msgs/Float64` для разобранных чисел; метаданные — модель моста,
параметры линии, состояние DTR/RTS, кодировка. `[N]`

6.3.2. Экспорт принятого текста в файл `.txt` с метками времени ДОЛЖЕН быть доступен для отправки
(Telegram и т. п.). `[N]`

### 6.4. Реестр приборов

6.4.1. Модуль ДОЛЖЕН сообщать реестру приборов модель, `deviceName`, номер канала и публикуемые
потоки. `[N]`

## 7. Нефункциональные требования

### 7.1. Быстродействие

7.1.1. Приём на скорости 921 600 бит/с непрерывного потока ДОЛЖЕН идти без потери байтов при
одновременной записи в MCAP и разборе чисел; подтверждается на оборудовании сравнением счётчика в
передаваемых строках. `[N]`

7.1.2. Задержка от прихода блока до показа строки на экране СЛЕДУЕТ держать не более 100 мс. `[N]`

7.1.3. Погрешность метки времени строки относительно момента передачи её первого байта целью СЛЕДУЕТ
держать не более 5 мс для FTDI с таймером 1 мс и CDC-ACM; подтверждается сравнением с захватом
логического анализатора. `[N]`

### 7.2. Надёжность

7.2.1. Ошибка или отключение порта НЕ ДОЛЖНЫ влиять на другие приборы сессии, в том числе на отладку
по тому же составному устройству. `[N]`

### 7.3. Память

7.3.1. Модуль НЕ ДОЛЖЕН выделять память на каждый блок во время приёма: буферы выделяются при
открытии и переиспользуются. `[N]`

### 7.4. Безопасность цели

7.4.1. Без включённой передачи (п. 4.5.1) модуль НЕ ДОЛЖЕН отправлять в bulk OUT ни одного байта.
`[N]`

### 7.5. Переносимость и сопровождаемость

7.5.1. Модуль `serial` (кадрирование, разбор, профиль) ДОЛЖЕН собираться и тестироваться на JVM 17
без Android SDK. `[N]` (р.1.1)

7.5.2. Каждое требование ДОЛЖНО быть прослеживаемо до кода и проверки (раздел 9). `[N]`

7.5.3. Зависимость usb-serial-for-android ДОЛЖНА быть указана с версией и уведомлением MIT в файле
лицензий третьих сторон. `[N]` (р.1.1)

7.5.4. Репозиторий JitPack ДОЛЖЕН подключаться в `settings.gradle.kts` через `exclusiveContent`
только
для группы `com.github.mik3y`, чтобы остальные зависимости не могли прийти оттуда. `[N]` (р.1.2)

## Приложение B. Соглашение о ссылках на ТЗ из кода

B.1. Ссылка на требование оформляется однострочным комментарием рядом с реализацией:
`// ТЗ UART 3.3.3`. Для нескольких требований — перечисление через запятую:
`// ТЗ UART 4.2.1, 4.2.3`.

B.2. Для тестов используется идентификатор тест-кейса и номера проверяемых требований, например:
`// TC-10: ТЗ UART 4.2.1–4.2.3`.

B.3. Пример:

```kotlin
// ТЗ UART 3.4.1: при закрытии DTR и RTS не трогаем — иначе плата может перезапуститься.
override fun close() { stopReceive(); releaseInterfaces() }
```

B.4. При удалении требования из документа его номер сохраняется с пометкой «(исключено)» (п. 1.6.2);
комментарий в коде удаляется вместе с реализацией.
