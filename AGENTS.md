# Правила для агентов

Этот файл читают ИИ-агенты (и люди), которые вносят изменения в репозиторий.

## Проект

HW Live Test — Android-приложение для работы с платой, на которой работает прошивка,
прямо с телефона: опознание отладчика и MCU, чтение памяти на ходу, графики, запись
mcap/rosbag, позже — логический анализатор WeAct на FX2. Без Termux, OpenOCD и GDB:
протокол ST-Link реализован на Kotlin поверх Android `UsbManager`.

Модули:

- `stlink` — чистый Kotlin/JVM: кодирование команд ST-Link, разбор ответов, опознание
  Cortex-M, STM32, AT32. Тестируется на JVM без Android.
- `usb` — Android-библиотека: поиск адаптеров по VID:PID, разрешения USB, bulk-транспорт.
- `app` — экраны.
- `telemetry` — чистый Kotlin/JVM: разбор `fields` из addresses.json, декодирование
  значений, проверка адресов по карте памяти, кольцевые ряды и оси графика.
- `diag` — чистый Kotlin/JVM: эвристики «ПУСК» (см. `docs/heuristics.md`).
- `firmware` — чистый Kotlin/JVM: Intel HEX, чтение Flash блоками, сверка.
- `recorder` — чистый Kotlin/JVM: запись MCAP (профиль ros1, `std_msgs/Float32` и т. п.),
  проверяется официальным читателем `mcap` для Python.
- `fx2la` — чистый Kotlin/JVM: протокол fx2lafw и загрузчика FX2, образ прошивки, пробный
  захват со статистикой каналов. Транспорт — в `usb` (`UsbFx2Transport`, асинхронные `UsbRequest`).

Концепция платформы — `docs/architecture.md`; требования к модулям — ТЗ в `docs/spec/`
(ST-Link, логический анализатор, USB-UART). Агент сверяет изменения модуля с его ТЗ, ставит в
коде ссылки вида `// ТЗ ST-Link 3.6.2`, а изменение поведения сопровождает новой ревизией ТЗ
(пометки `(р.X.Y)`, история ревизий, матрица прослеживаемости). Номера пунктов не меняются.

По умолчанию приложение только читает: без записи в память MCU, сброса и остановки ядра.
Допустимый побочный эффект — чтение DHCSR сбрасывает липкие S_RETIRE_ST/S_RESET_ST.
Регистры периферии не читаются «заодно» в составе блока (см. `ReadPlan`).

Изменение цели (прошивка, стирание, halt/go/reset) согласовано владельцем 22.10.2026 и
допускается только так, как описано в ТЗ прошивки и ТЗ ST-Link 2.0: в режиме эксперта, при
включённом режиме «Изменение цели» и с подтверждением каждого действия. Команды записи доступны
только через отдельный интерфейс, который нельзя получить без разрешения; `DebugMemory` остаётся
только для чтения. Option bytes и защиту Flash (RDP) приложение не меняет. Любое новое действие,
меняющее цель сверх этого списка, требует отдельного согласования. План — `docs/roadmap.md`.

## Коммиты

- Conventional Commits на английском: `feat(stlink): ...`, `fix(usb): ...`, `docs: ...`,
  `build: ...`, `ci: ...`, `test: ...`, `chore: ...`.
- Автор коммитов: `ViacheslavMezentsev <viacheslavmezentsev@ya.ru>`.
- В конце сообщения — трейлер `Co-Authored-By: <модель агента> <noreply@anthropic.com>`,
  например `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Без ссылок на сессии агента.

## Ветки и публикация

- Агент работает в ветке `claude/<задача>`, ответвлённой от свежего `origin/main`,
  и коммиты **не подписывает**.
- Агент не пушит в `main`, не подписывает коммиты, не ставит теги и не выпускает релизы.
- В `main` действует ruleset: подписанные коммиты, линейная история, без force push.
  `main` — ветка по умолчанию; на ветки `claude/*` ruleset не распространяется.
- Подпись делает только владелец: SSH-ключом, и только в репозиториях с remote
  на github.com (`includeIf "hasconfig:remote.*.url:..."` в глобальном `.gitconfig`).

### Цикл push → land

1. Ветка попадает на GitHub:
   - если у агента есть доступ к репозиторию — он пушит `claude/<задача>` без подписи,
     владелец переподписывает её (`git rebase --force-rebase origin/main`) и делает
     `git push --force-with-lease`;
   - если доступа нет — агент передаёт коммиты патчами (`git format-patch origin/main`)
     в локальный клон, владелец применяет их `git am` (коммиты подписываются сразу)
     в ветке от `origin/main` и делает `git push -u origin claude/<задача>`.
2. CI проходит на последнем коммите ветки.
3. Владелец выполняет `git land claude/<задача>`: `fetch`, ff-only `main` до
   `origin/main`, ff-only до **локальной** ветки, атомарный push `main` с удалением
   удалённой ветки, удаление локальной.

Особенности `land`, которые учитывает агент:

- сливается локальная ветка, поэтому перед `land` она должна совпадать с
  `origin/claude/<задача>`, прошедшей CI;
- слияние только fast-forward: если `main` ушёл вперёд, ветку сначала переносят
  на `origin/main` (rebase + повторный CI);
- после `land` ветки нет ни на GitHub, ни локально — следующая задача начинается
  с новой ветки от `origin/main`.

## Что не коммитить

- keystore, пароли, ключи подписи;
- серийные номера отладчиков и плат, уникальные ID микроконтроллеров (UID) в логах и тестах;
- личные пути (`C:\Users\...`, `/home/...`), `local.properties`;
- сборочные артефакты (`build/`, `*.apk`, `*.aab`).

Приложение не читает серийный номер USB-устройства и UID микроконтроллера. Записанные
логи для тестов (`stlink/src/test/resources/captures/`) перед коммитом проверяются на
отсутствие таких данных.

## Сборка и проверка

```shell
./gradlew test assembleDebug
```

CI (GitHub Actions) — два независимых процесса:

- `Android CI` (`android.yml`) — модульные тесты и отладочный APK (артефакт запуска).
  Не запускается, если в push изменены только `*.md`, `LICENSE` и настройки проверки
  документации.
- `Docs` (`docs.yml`) — запускается только при изменении `*.md`: markdownlint
  (`.markdownlint-cli2.jsonc`) и проверка локальных ссылок и якорей (lychee, без сети).

Локальная проверка до push (с 24.10.2026). Изменения копятся в ветке `claude/<задача>`
несколькими коммитами; агент передаёт ветку git-бандлом в `claude-patches\` клона владельца и
собирает её на Windows владельца через мост стенда (`stm32-gdbtest/tests/sandbox/06-stand-bridge`,
проба `probes/android_build.py`: клон бандла в `%LOCALAPPDATA%\hwlivetest-build`, `gradlew test
assembleDebug`, APK рядом с бандлом). Рабочую копию владельца сборка не трогает. Патчи для `git am`
агент выдаёт только после зелёной локальной сборки; CI на GitHub остаётся последней проверкой.

Версия (с 24.10.2026). Каждая сборка, отданная владельцу на установку, увеличивает последнее
число `appVersion` в `app/build.gradle.kts` (0.2.1 → 0.2.2 …). Версия видна в шапке каждого экрана
рядом с часами и в имени файла (`hwlivetest-<версия>-debug.apk`), поэтому по снимку экрана сразу
видно, установилась ли новая сборка.

Перед коммитом документации:

```shell
npx --yes markdownlint-cli2@0.18.1 "**/*.md"
```

## Отчёт в конце задачи

В конце каждой задачи агент пишет владельцу:

- версию программы (`appVersion`), время сборки и имя APK;
- точные команды PowerShell 7 для цикла push → land (применение патчей или
  переподпись, push ветки, проверка CI, `git land`);
- для аппаратной проверки — короткий план: что подключить, что нажать, какой лог прислать.

## Грабли

- В новом пустом репозитории первой на GitHub должна появиться `main`: первая
  запушенная ветка становится веткой по умолчанию и попадает под ruleset.
- Шаблоны `.gitignore` без `/` в начале действуют на любом уровне: `captures/`
  скрыл `stlink/src/test/resources/captures`. Перед коммитом агент проверяет
  `git status --ignored`.
- Сведения о протоколах из GPL-проектов (libsigrok, fx2lafw) берутся только как факты: коды
  запросов, раскладки, расчёты. Код не копируется и не переводится; источник и коммит указываются
  в ТЗ.
- Без Android SDK агент проверяет `app` компиляцией kotlinc против настоящего
  `android.jar` (API 35), а не самописных заглушек: заглушки пропустили метод
  `onStart()`, который совпал с методом жизненного цикла `Activity`.
